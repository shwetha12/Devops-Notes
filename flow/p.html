What Happens When an Application URL Is Hit?

Understanding the Complete Request Flow

Suppose a user opens the following URL: 

https://my-app.example.com/orders/123

The browser does not directly know which Pod should handle the request. The request travels through several layers. Each layer performs a specific function before the request finally reaches the application container.

The application may then retrieve data from a database, cache, another service, object storage, or another backend system and return the response through the same networking path.

Step 1 — User enters the application URL

The user enters: 

https://my-app.example.com/orders/123
  • The browser identifies the hostname: my-app.example.com.
  • The browser needs an IP address or network endpoint for that hostname.
  • DNS resolution is therefore performed.
  • The URL also contains the path /orders/123.
  • The HTTP method may be GET, POST, PUT, DELETE, etc., depending on the request.
The URL contains two useful pieces:
Hostname → identifies the application endpoint.
Path → identifies the requested application resource or API operation.
Step 2 — DNS finds the application endpoint

DNS translates the application hostname into the endpoint used to reach the application. 

my-app.example.com
        |
        | DNS lookup
        v
Application Endpoint
        |
        v
Load Balancer
  • The browser asks DNS for the address associated with the hostname.
  • The DNS response points the request toward the configured application endpoint.
  • In a cloud architecture, this can lead to a load balancer.
  • The browser then sends the HTTP/HTTPS request toward that endpoint.
Notes: DNS does not send the request to a Pod. DNS only helps the client locate the application endpoint.
Step 3 — Traffic reaches the load balancer

The load balancer receives the incoming network request and forwards traffic toward the application routing layer.

  • The request arrives at the configured load-balancing endpoint.
  • Network routing determines where the request can travel.
  • Security groups control permitted network traffic.
  • The load balancer can terminate TLS/HTTPS depending on the architecture.
  • The load balancer forwards the request toward the Kubernetes ingress or gateway layer.
Why the AWS networking resources matter:
VPC → provides the network boundary.
Subnets → provide network locations.
Route tables → determine traffic paths.
Security groups → control allowed traffic.
Load balancer → provides an entry point and forwards traffic.
Step 4 — Ingress or Gateway receives the request

The Kubernetes ingress or gateway layer determines where the request should go based on routing rules.

For example: 

Host:
my-app.example.com

Path:
/orders/123

my-app

  • The hostname can be checked.
  • The URL path can be checked.
  • Different paths can be routed to different Services.
  • Different hostnames can be routed to different applications.
  • The request is forwarded to the appropriate Kubernetes Service.
Notes: Ingress and Gateway are routing layers. The exact implementation depends on the Kubernetes ingress controller or gateway used.
Step 5 — Kubernetes Service finds the application Pods

The Service provides a stable Kubernetes network endpoint. It does not normally represent a single Pod. 

Service: my-app

selector:
    app = my-app

        |
        +----------------+
        |                |
        v                v
    Pod 1             Pod 2
    my-app            my-app
  • The Service has a selector such as app: my-app.
  • Pods created by the Deployment have the same label.
  • Kubernetes uses the selector to identify the matching Pods.
  • The Service provides a stable endpoint even when individual Pods change.
  • Traffic can be distributed among available matching Pods.
Why the Deployment label matters:
The Deployment creates Pods with the label app: my-app. The Service uses that same label to find those Pods.
Step 6 — Service sends traffic to a Pod

Kubernetes networking sends the request from the Service toward one of the matching application Pods. 

Ingress
   |
   v
Service: my-app
   |

   |

   |

  • The Service identifies healthy/available endpoints.
  • Traffic is directed toward an appropriate Pod.
  • The Pod has its own IP address, but the client normally uses the Service rather than the Pod IP directly.
  • Pods can be created, deleted, or replaced without changing the Service endpoint.
Notes: This is one reason Kubernetes Services are useful: Pods are dynamic, while the Service provides a stable abstraction for reaching the workload.
Step 7 — Pod sends the request to the application container

A Pod contains one or more containers. In a simple microservice deployment, the Pod may contain the main application container. 

Pod

       |

       |

  • The Pod receives the network traffic.
  • The container inside the Pod is listening on the configured application port.
  • The application process receives the HTTP request.
  • The application reads the URL path, HTTP method, headers, query parameters, and request body.

How Does the Application Get the Data?

Kubernetes does not normally contain the application's business data. Kubernetes runs the application. The application itself communicates with the required backend systems.

Database

The application can connect to a relational database, NoSQL database, or another data store to retrieve or update data.

Cache

A cache such as Redis can provide frequently accessed data faster than repeatedly querying the primary database.

Another Microservice

One microservice can call another service through its Kubernetes Service or another API endpoint.

S3

The application can use AWS SDKs and IAM permissions to retrieve or store objects in S3.

DynamoDB

An application can use AWS APIs to retrieve or update records stored in DynamoDB.

External API

The application can call an external service over HTTPS when the architecture requires information from another system.

  • The application runs inside a Kubernetes Pod.
  • The Pod can use a Kubernetes ServiceAccount.
  • The ServiceAccount can be associated with an AWS IAM role through the configured AWS/Kubernetes identity mechanism.
  • The IAM role contains policies defining allowed AWS actions.
  • The application uses AWS SDKs or APIs to access permitted resources.
Example:
If the application needs to read an S3 object, the workload requires an identity with permission such as s3:GetObject for the required bucket/object.

Complete Example: GET /orders/123

  • 1. The user opens https://my-app.example.com/orders/123.
  • 2. DNS resolves my-app.example.com to the configured application endpoint.
  • 3. The request reaches the configured load balancer.
  • 4. The load balancer forwards the request toward the Kubernetes ingress or gateway layer.
  • 5. The ingress/gateway checks the hostname and path and routes /orders/123 to the my-app Service.
  • 6. The Service uses its selector to identify matching application Pods.
  • 7. Kubernetes networking sends the request to an available my-app Pod.
  • 8. The application container receives the HTTP request.
  • 9. The application reads the order ID: 123.
  • 10. The application queries the required database or backend service.
  • 11. The backend returns the order information.
  • 12. The application creates an HTTP/JSON response.
  • 13. The response travels back through the Kubernetes networking and external load-balancing path.
  • 14. The browser receives the response and displays the requested information.
