Purpose

A self-service application portal can collect the information required to onboard and deploy a microservice.

Common Information

  • Application or service name
  • Repository information
  • Docker image or artifact information
  • Application version

  • Build information

  • Trigger infrastructure provisioning workflows.

EKS Provisioning

Amazon EKS

Amazon Elastic Kubernetes Service (EKS) is AWS's managed Kubernetes service. An EKS cluster provides the Kubernetes control plane and connects to compute resources where workloads run.

Common AWS Resources

  • VPC: Provides the network boundary for AWS resources.
  • Subnets: Provide network locations for EKS nodes and other AWS resources. EKS environments commonly use multiple Availability Zones.
  • Route Tables: Control how network traffic moves between subnets and other networks.
  • Internet Gateway: Provides internet connectivity for resources that require public network access.
  • NAT Gateway: Allows resources in private subnets to initiate outbound internet connections.
  • IAM: Controls permissions for AWS services, workloads, and infrastructure operations.
  • Security Groups: Provide network-level access controls for AWS resources.
  • KMS: Provides encryption key management for supported AWS resources.
  • EKS: Provides the managed Kubernetes control plane.
  • Node Groups: Provide compute capacity for Kubernetes workloads.

Resource Templates

Purpose

Resource Templates define reusable pieces of infrastructure, configuration, or automation that can be executed as part of an environment.

Terraform / OpenTofu → S3

Terraform or OpenTofu can create an S3 bucket for application data, artifacts, configuration, logs, or other AWS storage requirements.

Terraform / OpenTofu → IAM

IAM roles and policies can provide controlled permissions to applications, services, or AWS automation.

Vault Integration

HashiCorp Vault can provide centralized secret management. Applications and workloads can retrieve secrets without storing sensitive values directly in source code.

RSA / SSH

RSA keys or SSH-related configuration can be used for secure authentication to systems that require SSH-based access.

Other Application Prerequisites

Additional resources can include queues, databases, security configuration, DNS entries, certificates, storage, policies, or other application-specific dependencies.

Notes: These resources are environment or application prerequisites and are not universal Kubernetes requirements. The actual resources depend on what the application needs.
Terraform / OpenTofu Infrastructure

S3 Example

# Example: create an S3 bucket for application data

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "my_app" {
  bucket = "my-app-devops-demo-2026"

  tags = {
    Name        = "my-app"
    Environment = "dev"
  }
}

IAM Role Example

# Example: IAM role that can be assumed by an AWS service

resource "aws_iam_role" "my_app_role" {

  name = "my-app-dev-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"

    Statement = [{
      Effect = "Allow"

      Principal = {
        Service = "ecs-tasks.amazonaws.com"
      }

      Action = "sts:AssumeRole"
    }]
  })
}

IAM Policy Example

# Example: allow an application to read objects
# from the application S3 bucket

resource "aws_iam_policy" "my_app_s3_policy" {

  name = "my-app-s3-read"

  policy = jsonencode({
    Version = "2012-10-17"

    Statement = [{
      Effect = "Allow"

      Action = [
        "s3:GetObject",
        "s3:ListBucket"
      ]

      Resource = [
        "arn:aws:s3:::my-app-devops-demo-2026",
        "arn:aws:s3:::my-app-devops-demo-2026/*"
      ]
    }]
  })
}

KMS Example

# Example: create a KMS key for encryption

resource "aws_kms_key" "my_app" {

  description = "KMS key for my-app"

  enable_key_rotation = true

  tags = {
    Name = "my-app-kms"
  }
}

Helm Application Deployment

Helm

Helm is a package manager for Kubernetes. A Helm chart contains reusable templates and configuration used to generate Kubernetes resources.

Typical Chart Structure

my-app/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── namespace.yaml
    ├── deployment.yaml
    ├── service.yaml
    ├── configmap.yaml
    ├── secret.yaml
    ├── serviceaccount.yaml
    ├── ingress.yaml
    ├── hpa.yaml
    └── pvc.yaml

Chart.yaml

apiVersion: v2

name: my-app

description: Helm chart for my-app

type: application

version: 1.0.0

appVersion: "1.0.0"

values.yaml

replicaCount: 2

image:
  repository: 123456789012.dkr.ecr.us-east-1.amazonaws.com/my-app
  tag: "1.0.0"

service:
  type: ClusterIP
  port: 8080

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"

  limits:
    cpu: "500m"
    memory: "512Mi"

Namespace

# Creates a logical Kubernetes namespace.
# A namespace may also already exist and be managed elsewhere.

apiVersion: v1
kind: Namespace

metadata:
  name: my-app

Deployment

# Deployment manages the desired number of application Pods.
#
# replicas:
#   Defines how many Pod instances should normally run.
#
# selector:
#   Connects the Deployment to the Pods created by this template.
#
# template:
#   Defines the Pod specification.
#
# containers:
#   Defines the application container and Docker image.
#
# image:
#   Pulls the application image from Amazon ECR.
#
# ports:
#   Documents the port exposed by the application container.
#
# resources:
#   Defines CPU and memory requests/limits.

apiVersion: apps/v1
kind: Deployment

metadata:
  name: my-app
  namespace: my-app

spec:

  replicas: {{ .Values.replicaCount }}

  selector:
    matchLabels:
      app: my-app

  template:

    metadata:
      labels:
        app: my-app

    spec:

      containers:

        - name: my-app

          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

          ports:
            - containerPort: 8080

          resources:
            {{- toYaml .Values.resources | nindent 12 }}

Service

# Service provides a stable Kubernetes network endpoint
# for the application Pods.
#
# selector:
#   Finds Pods with the app=my-app label.
#
# port:
#   Port exposed by the Service.
#
# targetPort:
#   Port on which the container receives traffic.
#
# ClusterIP:
#   Makes the service reachable inside the Kubernetes cluster.

apiVersion: v1
kind: Service

metadata:
  name: my-app
  namespace: my-app

spec:

  type: {{ .Values.service.type }}

  selector:
    app: my-app

  ports:

    - port: {{ .Values.service.port }}

      targetPort: 8080

ConfigMap

# ConfigMap stores non-sensitive configuration.
# Examples include application mode, URLs, feature flags,
# and other environment-specific settings.

apiVersion: v1
kind: ConfigMap

metadata:
  name: my-app-config
  namespace: my-app

data:

  APP_NAME: "my-app"

  APP_ENVIRONMENT: "dev"

  LOG_LEVEL: "INFO"

Secret

# Secret stores sensitive configuration.
# Examples include passwords, tokens, or credentials.
#
# Sensitive values should normally be managed through
# an appropriate secret-management solution.

apiVersion: v1
kind: Secret

metadata:
  name: my-app-secret
  namespace: my-app

type: Opaque

stringData:

  APP_USERNAME: "my-app-user"

  APP_PASSWORD: "change-me"

ServiceAccount

# ServiceAccount provides an identity for a Kubernetes workload.
# It can be associated with AWS permissions through
# mechanisms such as IAM roles for service accounts.

apiVersion: v1
kind: ServiceAccount

metadata:
  name: my-app
  namespace: my-app

Ingress

# Ingress can expose HTTP/HTTPS application traffic.
# The actual behavior depends on the installed
# Kubernetes ingress controller or gateway implementation.

apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: my-app
  namespace: my-app

spec:

  rules:

    - host: my-app.example.com

      http:

        paths:

          - path: /

            pathType: Prefix

            backend:

              service:

                name: my-app

                port:

                  number: 8080

Horizontal Pod Autoscaler

# HPA adjusts the number of Pods based on resource
# utilization or other configured metrics.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler

metadata:
  name: my-app
  namespace: my-app

spec:

  scaleTargetRef:

    apiVersion: apps/v1
    kind: Deployment
    name: my-app

  minReplicas: 2

  maxReplicas: 5

  metrics:

    - type: Resource

      resource:

        name: cpu

        target:

          type: Utilization

          averageUtilization: 70

PersistentVolumeClaim

# PVC requests persistent storage for workloads
# that need data to survive Pod replacement.

apiVersion: v1
kind: PersistentVolumeClaim

metadata:
  name: my-app-data
  namespace: my-app

spec:

  accessModes:
    - ReadWriteOnce

  resources:

    requests:

      storage: 10Gi

Helm Commands

# Package/chart validation
helm lint ./my-app

# Render Kubernetes YAML without installing
helm template my-app ./my-app

# Install the application
helm install my-app ./my-app \
  --namespace my-app \
  --create-namespace

# Upgrade an existing release
helm upgrade my-app ./my-app \
  --namespace my-app

# View deployed Helm releases
helm list -A

Deployment

A Deployment describes the desired state of an application workload, including the number of replicas and the Pod template.

ReplicaSet

A ReplicaSet maintains the required number of matching Pods. Deployments normally create and manage ReplicaSets.

Pod

A Pod is the smallest deployable unit in Kubernetes. It contains one or more containers that share networking and storage resources.

Container

The container runs the application process using an image such as a Docker or OCI image.

Docker Image

The application image contains the application code, runtime, dependencies, and configuration required to run the application container.

Useful Kubernetes Commands

# List Pods
kubectl get pods -n my-app

# List Deployments
kubectl get deployments -n my-app

# List Services
kubectl get services -n my-app

# Show Pod details
kubectl describe pod <pod-name> -n my-app

# View application logs
kubectl logs <pod-name> -n my-app

# Show recent namespace events
kubectl get events -n my-app

# View all resources
kubectl get all -n my-app
Notes: Kubernetes continuously works toward the desired state defined by the workload resources. If a Pod fails, controllers can create another Pod to maintain the configured replica count.

Application Deployment Flow

Application information is first collected through a self-service interface. The information can then trigger a Backstage workflow that creates configuration and initiates downstream automation.

The infrastructure workflow can provision or connect to the required AWS environment, including an EKS cluster and its supporting AWS resources.

Rafay can then manage the Kubernetes environment using Projects, Environment Templates, Resource Templates, and Agents.

Resource Templates can execute infrastructure and configuration actions. Terraform or OpenTofu can be used to provision AWS resources such as S3 buckets and IAM resources, while other templates can configure secrets, keys, and application prerequisites.

Once the environment prerequisites are available, Helm can deploy the application resources into Kubernetes.

Kubernetes creates and manages the workload through the Deployment, ReplicaSet, Pod, and Container hierarchy. Services provide stable networking, while optional resources such as Ingress, HPA, PVC, ConfigMap, Secret, and ServiceAccount support additional application needs.

The final result is a running microservice inside the Kubernetes environment, with its infrastructure, configuration, networking, security, scaling, and monitoring components managed through the appropriate layers of the deployment platform.

Notes: The exact implementation varies between organizations and applications. Existing AWS infrastructure can be reused, different infrastructure-as-code tools can be used, and some Kubernetes resources may be managed by separate platform or GitOps processes.
