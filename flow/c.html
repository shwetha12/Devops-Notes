DevOps

Application Deployment Path

1. Internal Portal

Application onboarding information is entered to start the deployment and environment workflow.

Typical information
Application / Microservice
Identifies the application that will be deployed.
Application Version
Identifies the application release or version being deployed.
Docker Image / Artifact
Identifies the application package or container image to deploy.
Target Environment
Identifies where the application should be deployed.
↓

2. Backstage Workflow API

The Internal Portal calls the Backstage workflow/API to start the automation.

Internal Portal
Sends the application and environment information through an API request.
↓
Backstage Workflow
Orchestrates the provisioning and configuration steps defined by the automation.
↓

3. EKS Provisioning

AWS infrastructure and the Kubernetes environment are created or prepared.

Common components
VPC
Provides the isolated AWS network in which the Kubernetes environment operates.
Subnets
Divide the VPC into network segments where cluster and application resources can run.
↳ Public Subnets
↳ Private Subnets
Routing
Controls how traffic moves between the VPC, subnets, AWS services, and external networks.
↳ Route Tables
↳ Internet Gateway
↳ NAT Gateway
IAM
Provides AWS identities and permissions required by EKS, worker nodes, and workloads.
↳ EKS Cluster Role
↳ Node Role
↳ IAM Policies
Security Groups
Control inbound and outbound network traffic for AWS resources.
KMS
Provides encryption keys when encryption is required for cluster or application data.
EKS
Provides the managed Kubernetes control plane for running containerized workloads on AWS.
Node Groups
Provide the worker compute capacity where Kubernetes Pods run.
↳ EC2 Worker Nodes
EKS Add-ons
Provide common Kubernetes/AWS integration components needed by the cluster.
↳ VPC CNI
↳ CoreDNS
↳ kube-proxy
↳ EBS CSI Driver
↓

EKS Cluster Ready

The Kubernetes platform is available for the application environment and workload deployment.

↓

4. Rafay

The application environment is launched and the required resource templates are executed.

Project
Provides a logical boundary for organizing environments, resources, and application deployments.
Environment Template
Defines the collection of resources and automation used to create an application environment.
Rafay Agent
Provides the execution mechanism used to communicate with and manage resources in the environment.
↓

5. Resource Templates

Supporting infrastructure and application prerequisites are provisioned before application deployment.

Infrastructure / application prerequisites
Terraform / OpenTofu → S3
Provides object storage for application data, files, artifacts, configuration, or other application-specific storage needs.
Terraform / OpenTofu → IAM
Provides AWS permissions required by the application or supporting AWS services.
Terraform / OpenTofu → Vault Integration
Provides secure access to application secrets without placing sensitive values directly in application configuration or source code.
Terraform / OpenTofu → RSA / SSH Configuration
Provides key-based authentication when an application or supporting process requires secure SSH access.
Other Application Prerequisites
Additional AWS resources, configuration, or integrations required by a particular application.
↓

Application Environment Ready

Required supporting resources are available and the application can proceed to Kubernetes deployment.

↓

6. Helm Application Deployment

Helm renders the application templates and creates the Kubernetes resources required to run the application.

Common Kubernetes resources
Namespace
Provides a logical boundary for organizing application resources inside the cluster.
Deployment
Defines the desired number of application Pods and manages application rollout and replacement.
Service
Provides a stable network endpoint and routes traffic to the application's Pods.
ConfigMap
Stores non-sensitive application configuration separately from the container image.
Secret / Secret Reference
Provides sensitive configuration or references to an external secret-management system.
ServiceAccount
Provides an identity for the Kubernetes workload and can be associated with permissions when required.
Ingress / Gateway
Provides an entry point for external HTTP/HTTPS traffic when external access is required.
HPA
Automatically adjusts the number of application Pods based on configured metrics such as CPU utilization.
PVC
Requests persistent storage when the application needs data to survive Pod replacement.
↓

7. Kubernetes Workload

Kubernetes creates and manages the application workload.

Deployment
Defines the desired application state.
↓
ReplicaSet
Maintains the required number of Pods.
↓
Pod
The Kubernetes execution unit that contains one or more application containers.
↓
Container
Runs the application process from the container image.
↓
Docker Image
Contains the application code and required runtime dependencies.
↓

8. Microservice Running

The application is running as a Kubernetes workload and is available through its configured service or endpoint.

1. Internal Portal — Details

The Internal Portal is the entry point where the application and deployment information is collected.

Typical inputs

  • Application / microservice name
  • Application version
  • Docker image or artifact
  • Target environment
  • Deployment configuration
  • Security/scanning information when required
2. Backstage Workflow API — Details

The Internal Portal sends the application information to a Backstage API or workflow.

Internal Portal → Backstage API / Workflow

Backstage then orchestrates the automation needed for the next provisioning steps.

Depending on the templates and automation configured, the workflow can create project/configuration information and initiate environment provisioning.

3. EKS Provisioning — Details

Amazon EKS provides a managed Kubernetes control plane. The surrounding AWS resources provide networking, security, identity, and compute for the cluster.

High-level provisioning sequence

  ↓
Routing
  ↓
Security Groups
  ↓
IAM
  ↓
EKS

Important: The exact infrastructure depends on the environment. For example, an existing VPC and subnets may be reused instead of being created as part of the EKS provisioning.

5. Resource Templates — Details

Resource Templates are used to provision supporting infrastructure or configuration required by the application environment.

Terraform / OpenTofu

Terraform or OpenTofu can describe infrastructure as code. The Resource Template can execute that automation and expose the resulting status, outputs, and logs.

S3 — Example

# Create S3 storage for my-app.
#
# S3 can be used for application files, data,
# reports, artifacts, or other object storage needs.

resource "aws_s3_bucket" "my_app" {

  bucket = "my-app-application-data"

  tags = {

    Name = "my-app-application-data"

    Application = "my-app"
  }
}

IAM Role — Example

# Create an IAM role for my-app.
#
# The trust policy determines which AWS identity/service
# is allowed to assume this role.
#
# The actual trust relationship depends on the workload
# architecture.

resource "aws_iam_role" "my_app" {

  name = "my-app-role"

  assume_role_policy = jsonencode({

    Version = "2012-10-17"

    Statement = [

      {

        Effect = "Allow"

        Principal = {

          Service = "eks.amazonaws.com"
        }

        Action = "sts:AssumeRole"
      }
    ]
  })

  tags = {

    Application = "my-app"
  }
}

IAM Policy — Example

# Example policy allowing my-app to read
# objects from its S3 bucket.
#
# In production, permissions should follow
# least-privilege principles.

resource "aws_iam_policy" "my_app_s3" {

  name = "my-app-s3-access"

  policy = jsonencode({

    Version = "2012-10-17"

    Statement = [

      {

        Effect = "Allow"

        Action = [

          "s3:GetObject",

          "s3:ListBucket"
        ]

        Resource = [

          aws_s3_bucket.my_app.arn,

          "${aws_s3_bucket.my_app.arn}/*"
        ]
      }
    ]
  })
}

KMS — Example

# Example KMS key for application encryption.
#
# KMS can be used when application or infrastructure
# data needs encryption using a customer-managed key.

resource "aws_kms_key" "my_app" {

  description = "KMS key for my-app"

  enable_key_rotation = true

  tags = {

    Name = "my-app-kms"

    Application = "my-app"
  }
}

Terraform Outputs

# Outputs make useful resource information available
# to later automation steps.

output "my_app_bucket" {

  description = "S3 bucket for my-app"

  value = aws_s3_bucket.my_app.bucket
}

output "my_app_role" {

  description = "IAM role for my-app"

  value = aws_iam_role.my_app.arn
}

Basic Terraform Execution

# Initialize Terraform providers/modules.

terraform init

# Review the infrastructure changes.

terraform plan

# Create or update the resources.

terraform apply
Resource Template execution: The Terraform/OpenTofu execution can produce resource status, input values, output values, and execution logs.

Vault Integration

Vault or another secrets-management system can provide application secrets securely at deployment or runtime.

Avoid putting passwords, tokens, or private keys directly into Git repositories, Terraform source, or Helm values. The exact secret-injection mechanism depends on the environment.

RSA / SSH

RSA/SSH configuration may be required when an application or supporting process needs secure key-based authentication.

RSA/SSH is an application/environment-specific prerequisite; it is not required by every Kubernetes application.

Other Application Prerequisites

Additional resources can be added depending on what the application requires.

  • AWS storage
  • IAM permissions
  • Secrets
  • Security configuration
  • Application-specific AWS services
  • Environment configuration
6. Helm Application Deployment — Details

Helm packages Kubernetes resources into a reusable chart. The chart uses values to create the Kubernetes objects required by the application.

Basic Helm Structure

my-app/
│
├── Chart.yaml
│
├── values.yaml
│
└── templates/
    │
    ├── namespace.yaml
    ├── deployment.yaml
    ├── service.yaml
    ├── configmap.yaml
    ├── secret.yaml
    ├── serviceaccount.yaml
    ├── ingress.yaml
    ├── hpa.yaml
    └── pvc.yaml

Chart.yaml

# Defines the Helm chart.

apiVersion: v2

name: my-app

description: Helm chart for my-app

type: application

version: 1.0.0

appVersion: "1.0.0"

values.yaml

# ==========================================================
# values.yaml
#
# This file contains values used by the Helm templates.
#
# The same chart can be reused across environments by
# changing values instead of changing the Kubernetes templates.
# ==========================================================


# ----------------------------------------------------------
# Application name
# ----------------------------------------------------------

name: my-app


# ----------------------------------------------------------
# Namespace
#
# Keeps application resources logically separated.
# ----------------------------------------------------------

namespace: my-app


# ----------------------------------------------------------
# Docker image
#
# repository = location of the image
# tag        = version of the application
# ----------------------------------------------------------

image:

  repository: "my-app"

  tag: "1.0.0"

  pullPolicy: IfNotPresent


# ----------------------------------------------------------
# Number of Pods
# ----------------------------------------------------------

replicaCount: 2


# ----------------------------------------------------------
# Kubernetes Service
#
# The Service gives the application a stable network endpoint.
# ----------------------------------------------------------

service:

  type: ClusterIP

  port: 8080

  targetPort: 8080


# ----------------------------------------------------------
# Application configuration
#
# These are non-sensitive values.
# Sensitive values should come from a secret-management
# mechanism instead of being stored here.
# ----------------------------------------------------------

config:

  environment: "dev"

  logLevel: "INFO"


# ----------------------------------------------------------
# Container resource requests and limits
#
# requests = resources Kubernetes should reserve
# limits   = maximum resources the container can consume
# ----------------------------------------------------------

resources:

  requests:

    cpu: "250m"

    memory: "256Mi"


  limits:

    cpu: "500m"

    memory: "512Mi"


# ----------------------------------------------------------
# Health check
#
# Kubernetes uses these endpoints to determine application
# health and readiness.
# ----------------------------------------------------------

health:

  path: "/health"

  port: 8080


# ----------------------------------------------------------
# Autoscaling
# ----------------------------------------------------------

autoscaling:

  enabled: true

  minReplicas: 2

  maxReplicas: 5

  targetCPUUtilization: 70

templates/namespace.yaml

{{/*
Creates the Kubernetes namespace for my-app.

A namespace provides logical separation for Kubernetes resources.

Some environments create namespaces separately, so this template
may not be needed if the namespace already exists.
*/}}

apiVersion: v1

kind: Namespace

metadata:

  name: {{ .Values.namespace }}

templates/deployment.yaml

{{/*
==============================================================
Deployment
==============================================================

The Deployment is the main Kubernetes workload definition.

It tells Kubernetes:

1. How many Pods should run.
2. Which Docker image should run.
3. Which container port is used.
4. Which configuration should be provided.
5. CPU and memory requirements.
6. How to check application health.

Deployment
    ↓
ReplicaSet
    ↓
Pods
    ↓
Containers
    ↓
Docker Image
==============================================================
*/}}


apiVersion: apps/v1

kind: Deployment


metadata:

  # Helm release name makes the resource name unique.

  name: {{ .Release.Name }}-my-app

  namespace: {{ .Values.namespace }}


  labels:

    app: my-app


spec:

  # ----------------------------------------------------------
  # Number of desired Pods.
  #
  # If replicaCount = 2, Kubernetes tries to keep
  # two healthy Pods running.
  # ----------------------------------------------------------

  replicas: {{ .Values.replicaCount }}


  # ----------------------------------------------------------
  # Selector tells the Deployment which Pods it manages.
  # It must match the labels in the Pod template.
  # ----------------------------------------------------------

  selector:

    matchLabels:

      app: my-app


  template:

    metadata:

      labels:

        app: my-app


    spec:

      containers:

        - name: my-app


          # --------------------------------------------------
          # Docker image
          #
          # Example:
          # my-app:1.0.0
          #
          # In a real environment this can point to ECR
          # or another container registry.
          # --------------------------------------------------

          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"


          # Controls when Kubernetes pulls the image.

          imagePullPolicy: {{ .Values.image.pullPolicy }}


          # --------------------------------------------------
          # Container port
          # --------------------------------------------------

          ports:

            - name: http

              containerPort: {{ .Values.service.targetPort }}

              protocol: TCP


          # --------------------------------------------------
          # Environment variables
          #
          # These values come from values.yaml.
          # --------------------------------------------------

          env:

            - name: APP_ENV

              value: "{{ .Values.config.environment }}"


            - name: LOG_LEVEL

              value: "{{ .Values.config.logLevel }}"


          # --------------------------------------------------
          # Resource requests and limits
          #
          # requests tell Kubernetes the minimum resources
          # the application should have available.
          #
          # limits prevent the container from exceeding
          # the configured maximum.
          # --------------------------------------------------

          resources:

            {{- toYaml .Values.resources | nindent 12 }}


          # --------------------------------------------------
          # Readiness Probe
          #
          # Determines whether the application is ready
          # to receive traffic.
          #
          # If the application is not ready, Kubernetes
          # does not send Service traffic to that Pod.
          # --------------------------------------------------

          readinessProbe:

            httpGet:

              path: {{ .Values.health.path }}

              port: {{ .Values.health.port }}

            initialDelaySeconds: 10

            periodSeconds: 10

            timeoutSeconds: 5

            failureThreshold: 3


          # --------------------------------------------------
          # Liveness Probe
          #
          # Determines whether the application is still alive.
          #
          # If the application repeatedly fails the liveness
          # check, Kubernetes can restart the container.
          # --------------------------------------------------

          livenessProbe:

            httpGet:

              path: {{ .Values.health.path }}

              port: {{ .Values.health.port }}

            initialDelaySeconds: 30

            periodSeconds: 20

            timeoutSeconds: 5

            failureThreshold: 3

templates/service.yaml

{{/*
==============================================================
Service
==============================================================

Pods are temporary.

A Pod can be recreated and receive a different IP address.

The Service provides a stable network endpoint and sends
traffic to Pods matching the "app: my-app" label.

Traffic flow:

Client
  ↓
Service
  ↓
my-app Pods
==============================================================
*/}}


apiVersion: v1

kind: Service


metadata:

  name: {{ .Release.Name }}-my-app

  namespace: {{ .Values.namespace }}


spec:

  type: {{ .Values.service.type }}


  # ----------------------------------------------------------
  # Find Pods using this label.
  # ----------------------------------------------------------

  selector:

    app: my-app


  ports:

    - name: http

      port: {{ .Values.service.port }}

      targetPort: {{ .Values.service.targetPort }}

      protocol: TCP

templates/configmap.yaml

{{/*
==============================================================
ConfigMap

Stores non-sensitive configuration.

Examples:

APP_ENV
LOG_LEVEL
Application URLs
Feature flags

Do NOT put passwords or tokens in a ConfigMap.
==============================================================
*/}}


apiVersion: v1

kind: ConfigMap


metadata:

  name: {{ .Release.Name }}-my-app-config

  namespace: {{ .Values.namespace }}


data:

  APP_ENV: "{{ .Values.config.environment }}"

  LOG_LEVEL: "{{ .Values.config.logLevel }}"

templates/secret.yaml

{{/*
==============================================================
Secret

Kubernetes Secret can store sensitive configuration.

For production environments, secrets are often retrieved
from an external secrets-management system such as Vault.

The example below demonstrates the Kubernetes resource
structure only.

Do not commit real passwords, tokens, or private keys to Git.
==============================================================
*/}}


apiVersion: v1

kind: Secret


metadata:

  name: {{ .Release.Name }}-my-app-secret

  namespace: {{ .Values.namespace }}


type: Opaque


stringData:

  example-key: "replace-with-secret-reference"

templates/serviceaccount.yaml

{{/*
==============================================================
ServiceAccount

Provides an identity for the Kubernetes workload.

It can be associated with permissions when the application
needs to access Kubernetes or AWS resources.

The exact AWS integration depends on the EKS identity
configuration.
==============================================================
*/}}


apiVersion: v1

kind: ServiceAccount


metadata:

  name: {{ .Release.Name }}-my-app

  namespace: {{ .Values.namespace }}


  labels:

    app: my-app

templates/ingress.yaml

{{/*
==============================================================
Ingress

Ingress provides an HTTP/HTTPS entry point to the application.

Typical traffic:

Internet / Client
      ↓
Load Balancer / Ingress
      ↓
Service
      ↓
Pods

The exact annotations depend on the ingress controller
or gateway implementation used by the Kubernetes platform.
==============================================================
*/}}


apiVersion: networking.k8s.io/v1

kind: Ingress


metadata:

  name: {{ .Release.Name }}-my-app

  namespace: {{ .Values.namespace }}


spec:

  rules:

    - host: my-app.example.com

      http:

        paths:

          - path: /

            pathType: Prefix

            backend:

              service:

                name: {{ .Release.Name }}-my-app

                port:

                  number: {{ .Values.service.port }}

templates/hpa.yaml

{{/*
==============================================================
Horizontal Pod Autoscaler

HPA adjusts the number of Pods based on metrics.

Example:

CPU increases
     ↓
HPA detects higher utilization
     ↓
More Pods
     ↓
More application capacity

This resource is optional.
==============================================================
*/}}


{{- if .Values.autoscaling.enabled }}

apiVersion: autoscaling/v2

kind: HorizontalPodAutoscaler


metadata:

  name: {{ .Release.Name }}-my-app

  namespace: {{ .Values.namespace }}


spec:

  scaleTargetRef:

    apiVersion: apps/v1

    kind: Deployment

    name: {{ .Release.Name }}-my-app


  minReplicas: {{ .Values.autoscaling.minReplicas }}

  maxReplicas: {{ .Values.autoscaling.maxReplicas }}


  metrics:

    - type: Resource

      resource:

        name: cpu

        target:

          type: Utilization

          averageUtilization: {{ .Values.autoscaling.targetCPUUtilization }}

{{- end }}

templates/pvc.yaml — Optional

{{/*
==============================================================
PersistentVolumeClaim

PVC requests persistent storage for an application.

Use it when application data must survive Pod replacement.

For example:

Pod deleted
   ↓
New Pod created
   ↓
Same persistent storage can be mounted

PVC is optional. Stateless applications may not need it.
==============================================================
*/}}


apiVersion: v1

kind: PersistentVolumeClaim


metadata:

  name: {{ .Release.Name }}-my-app-data

  namespace: {{ .Values.namespace }}


spec:

  accessModes:

    - ReadWriteOnce


  resources:

    requests:

      storage: 10Gi

Basic Helm Deployment

# Validate/render the chart before deployment.
#
# This helps identify template or values problems.

helm template my-app ./my-app \
  --namespace my-app


# Install the application for the first time.

helm install my-app ./my-app \
  --namespace my-app \
  --create-namespace


# Upgrade the application when a new version is deployed.

helm upgrade my-app ./my-app \
  --namespace my-app


# Check the Helm release.

helm list \
  --namespace my-app


# Check application Pods.

kubectl get pods \
  --namespace my-app


# Check the Deployment.

kubectl get deployment \
  --namespace my-app


# Check the Service.

kubectl get service \
  --namespace my-app


# View application logs.

kubectl logs \
  deployment/my-app-my-app \
  --namespace my-app

Helm Chart → values.yaml → Kubernetes Templates → Kubernetes Resources → Deployment → Pods → Containers → Docker Image

How Everything Works Together

1. Application Request
Application information is entered in the Internal Portal.
↓
2. Workflow Trigger
The Internal Portal calls the Backstage workflow/API.
↓
3. Platform Provisioning
The workflow provisions or prepares the AWS infrastructure and EKS Kubernetes cluster.

VPC → Subnets → Routing → IAM → Security → EKS → Node Groups → Add-ons
↓
4. Kubernetes Environment Ready
The EKS cluster is available to run Kubernetes workloads.
↓
5. Environment Resources
Rafay launches the environment and executes the required Resource Templates.

Resource Templates can execute Terraform/OpenTofu to provision supporting application resources such as S3, IAM, Vault integration, RSA/SSH configuration, and other prerequisites.
↓
6. Application Environment Ready
The infrastructure and supporting resources needed by the application are available.
↓
7. Application Deployment
Helm uses the chart, values, and Docker image information to create the Kubernetes resources.

Namespace → Deployment → Service → ConfigMap / Secret / ServiceAccount → Ingress / Gateway / HPA when required
↓
8. Kubernetes Creates the Workload
Deployment creates/manages ReplicaSets, which maintain the required Pods.

Deployment → ReplicaSet → Pod → Container → Docker Image
↓
9. Application Running
The microservice is running inside the Kubernetes cluster and can receive traffic through its configured Service and external routing mechanism.
