8. Microservice Running

Application is running as a workload on the Kubernetes cluster

1. Internal Portal — What happens here?

The internal portal provides the application onboarding information needed to start the workflow.

  • Application / microservice name
  • Application version
  • Artifact or Docker image information
  • Target environment
  • Build / deployment information
  • Security or scanner information when required
The important interview point: the portal is the entry point for the application request.
2. Backstage Workflow API — How is it triggered?

The Internal Portal calls a Backstage workflow/API after the required application information is submitted.

Backstage then orchestrates the next steps of the provisioning workflow.

Simple interview explanation: Internal Portal → Backstage API / Workflow → Provisioning
3. EKS Cluster Provisioning — What gets provisioned?

The goal is to create or prepare the AWS environment in which Kubernetes workloads can run.

  • VPC and networking
  • Public/private subnets
  • Route tables
  • Internet Gateway / NAT Gateway where required
  • Security Groups
  • IAM roles and policies
  • KMS / encryption where enabled
  • EKS control plane
  • Managed node groups / EC2 worker nodes
  • EKS add-ons
These are common AWS/EKS components. The exact resources depend on how the environment is designed.
4. Rafay Environment Template — What does it do?

Once the Kubernetes environment is available, the environment workflow can be launched through Rafay.

  • Rafay Project provides the organizational boundary.
  • Environment Template defines the environment workflow.
  • Resource Templates define individual provisioning resources.
  • Rafay Agent can execute the environment workflow.

The Environment Template coordinates the resources required for the application environment.

5. Resource Templates — What resources are provisioned?

Resource Templates can execute infrastructure-as-code or configuration needed by the application environment.

A common implementation uses Terraform or OpenTofu.

  • S3 / application storage
  • IAM roles and policies
  • Secrets / Vault integration
  • Security and access configuration
  • Other AWS resources required by the application
  • Environment-specific configuration
Important: Kubernetes does not universally require all of these. They are common application/environment prerequisites.

During execution, the platform can provide resource status, input/output values, and execution logs.

6. Helm — What is needed to deploy an application?

Helm packages Kubernetes application resources into a reusable chart.

Common deployment inputs include:

  • Helm chart
  • values.yaml
  • Environment-specific values
  • Docker image repository
  • Docker image tag/version
  • Namespace

The Helm chart can create the Kubernetes resources required by the application.

Common resources include:

  • Deployment
  • Service
  • ConfigMap — when required
  • Secret / Secret reference — when required
  • ServiceAccount — when required
  • Ingress / Gateway — when required
  • HPA — when required
  • PVC — when required
7. Kubernetes Workload — What happens after Helm?

Helm applies the Kubernetes manifests/templates. Kubernetes then creates and manages the workload.

The basic relationship to remember is:

Deployment
↓

↓

The Deployment maintains the desired number of Pods. The Pod runs the container, and the container runs the application image.
