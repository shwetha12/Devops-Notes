2. CI/CD and DevOps

5. Explain a CI/CD pipeline end to end.

A typical pipeline starts with source control and a code change. The pipeline builds and packages the application, runs unit and automated tests, performs quality and security checks, publishes a versioned artifact, and deploys that artifact through environments such as development, test, UAT, and production. Production promotion normally includes approvals, change controls, deployment validation, monitoring, and a rollback path.

6. What is the difference between CI and CD?

Continuous Integration focuses on frequently integrating code and automatically building and testing it. Continuous Delivery or Deployment extends the process toward automated promotion and deployment into environments.

7. What is Build Once, Deploy Many?

The application is built once to create a versioned artifact, and that same artifact is promoted through the environments. The artifact is not rebuilt separately for each environment. Environment-specific configuration is applied during deployment. This improves consistency and traceability.

8. What is an artifact?

An artifact is a versioned output produced by the build process, such as a package, binary, container image, or deployment bundle. Artifact management allows the exact tested version to be promoted across environments.

9. What is a quality gate?

A quality gate is a predefined condition that must pass before the pipeline can continue. Examples include code-quality thresholds, unit-test results, code coverage, security scans, or vulnerability thresholds.

3. Azure DevOps

10. Your strongest CI/CD experience is Jenkins. How would you work with Azure DevOps?

My strongest hands-on CI/CD experience has been Jenkins, but the underlying concepts are transferable. I have worked with source control, automated builds, testing, artifacts, deployment stages, environment promotion, approvals, production validation, and troubleshooting. In Azure DevOps, I would map those concepts to Azure Repos, Pipelines, Artifacts, and Environments while learning the team's specific pipeline architecture, branching strategy, approvals, checks, and deployment controls.

11. What are the main Azure DevOps components relevant to this role?

Azure Repos provides source control and Git workflows. Azure Pipelines provides CI/CD automation. Azure Artifacts provides package and artifact management. Azure Boards supports work tracking. For this role, the most important areas are Repos, Pipelines, Artifacts, Environments, approvals, checks, and deployment visibility.

12. What is an Azure DevOps multi-stage pipeline?

It is a pipeline divided into logical stages such as Build, Test, Dev, QA, UAT, and Production. Each stage can contain jobs and tasks and can have conditions, approvals, or checks controlling whether the pipeline can proceed.

13. What are Azure DevOps environments?

Environments represent deployment targets such as Dev, Test, UAT, or Production. They provide deployment visibility and can have controls such as approvals and checks before a deployment proceeds.

14. What are approvals and checks?

They are controls used to prevent a pipeline from progressing until required conditions are satisfied. For example, a production environment can require an approval or other validation before deployment is allowed.

15. What is a YAML pipeline?

A YAML pipeline defines CI/CD configuration as code. It can contain stages, jobs, tasks, variables, conditions, and deployment logic, allowing pipeline configuration to be version-controlled.

16. What is a service connection?

A service connection provides a controlled way for Azure DevOps pipelines to authenticate to an external service or deployment target, such as a cloud environment or another system.

17. How would you troubleshoot a failed Azure DevOps pipeline?

I would identify the failed stage and job, review the task output and logs, compare the failure with previous successful runs, and determine whether it is a source, build, dependency, authentication, artifact, environment, configuration, or deployment problem. I would then identify the appropriate owner and coordinate resolution.

18. How would you manage a production deployment in Azure DevOps?

I would verify the correct source version and artifact, confirm testing and environment readiness, review dependencies, verify the ServiceNow change and required approvals, confirm implementation and rollback plans, and verify production environment approvals or checks. After deployment, I would coordinate smoke testing, application validation, and monitoring.

19. What deployment strategies do you know?

Rolling, blue-green, canary, and recreate are common strategies. The appropriate strategy depends on application architecture, downtime requirements, traffic management, rollback needs, risk, and business requirements.

4. Release Management

20. What is your release-management experience?

I have coordinated with application and shared-services teams to understand deployment processes, identify blockers, support production releases, and validate applications after deployment.

21. How do you determine whether a release is production-ready?

I review code and build readiness, testing and UAT results, artifact readiness, environment and infrastructure readiness, application and integration dependencies, database changes, ServiceNow change approval, implementation and rollback plans, monitoring, validation steps, and stakeholder readiness. I also check for conflicting changes.

22. How do you identify release dependencies?

I review the application architecture and identify upstream and downstream dependencies involving applications, APIs, databases, middleware, infrastructure, networks, cloud services, and external systems. I also review CMDB relationships and related change records and confirm dependencies with the appropriate technical teams.

23. How do you assess release risk?

I consider probability and impact. Factors include business criticality, number of affected applications or users, infrastructure or database changes, integrations, downtime, complexity, testing coverage, dependency uncertainty, previous change history, and rollback difficulty.

24. How do you manage multiple releases at the same time?

I prioritize by business impact, technical risk, dependencies, timing, and production criticality. I maintain visibility of current and upcoming releases, identify conflicts early, and coordinate sequencing when multiple changes affect the same application, CI, environment, or dependency.

25. How would you provide visibility into what changed, what is changing, and what is coming next?

I would maintain a consolidated release view connecting application changes, pipeline deployments, ServiceNow changes, affected CIs, dependencies, environments, production status, and upcoming releases. This allows teams to identify conflicts, dependencies, and risk before implementation.

5. ServiceNow Change and Release Management

26. What is Risk Assessment in ServiceNow?

Risk Assessment evaluates the risk of a proposed change. The requester or change team answers configured questions covering areas such as impact, complexity, testing, dependencies, business criticality, outage potential, and rollback capability. ServiceNow evaluates those responses and produces an assessment result.

27. What types of questions are asked during Risk Assessment?

Typical questions address business impact, affected applications or CIs, users or services affected, outage or degradation, testing status, dependencies, rollback availability, rollback complexity, previous change history, and other scheduled changes. The exact questionnaire is organization-specific.

28. What is Risk Calculation?

Risk Calculation determines change risk using configured conditions or rules. Factors can include change type, impact, affected CI, timing, and other organization-specific conditions.

29. What is the difference between Risk Assessment and Risk Calculation?

Risk Assessment is generally questionnaire-based and uses answers about the proposed change. Risk Calculation uses configured rules or conditions to determine risk. An organization can use either or both.

30. What if the application team says the change is Low Risk but ServiceNow calculates High Risk?

I would review the assessment responses and identify which factors caused the higher result. If an answer is incorrect, it should be corrected with justification. If the high-risk result is accurate, the change should follow the higher-risk approval process rather than lowering the risk simply to proceed.

31. How do testing and rollback affect risk?

Complete testing and a clear, proven rollback approach reduce implementation and recovery risk. Incomplete testing, unknown dependencies, significant production impact, or difficult recovery can increase risk.

32. What are Low, Moderate, and High Risk?

They represent progressively greater levels of potential impact, complexity, or recovery risk. The exact thresholds and approval paths depend on organizational policy and ServiceNow configuration.

33. How does risk affect approval?

Risk helps determine the level of review and approval required. Higher-risk changes may require additional approvals or CAB review, while lower-risk changes may follow a simpler workflow according to organizational policy.

34. Can production deployment happen before required approvals?

No. Required approvals should be completed before production implementation. The purpose of change management is to ensure that the production change has been reviewed and authorized before deployment.

35. What if an approver rejects the change?

The rejection reason should be reviewed. The implementation, testing, risk, impact, or rollback information should be corrected or strengthened as necessary, and the change should be resubmitted through the required approval process.

6. CAB, Scheduling and Go / No-Go

36. What is CAB?

CAB stands for Change Advisory Board. It reviews planned changes from technical, business, risk, impact, timing, testing, dependency, implementation, and rollback perspectives.

37. Does every production change go through CAB?

No. It depends on the organization's policy, change type, and risk. Standard changes may be pre-authorized, normal changes follow the configured approval process and may require CAB, and emergency changes follow an expedited process.

38. What does CAB review for a high-risk change?

CAB reviews what is changing, why it is needed, affected applications or CIs, business and technical impact, risk, testing, implementation plan, dependencies, timing, validation, and rollback.

39. Does CAB perform the deployment?

Normally, no. CAB provides governance and approval. The actual deployment is normally performed by the DevOps, release, or deployment team through the approved CI/CD process.

40. What is a change window?

A change window is the approved period during which the production implementation is scheduled. Before the window, approvals, artifacts, implementation steps, rollback, dependencies, validation, and team availability should be confirmed.

41. What is conflict detection?

Conflict detection identifies overlapping or potentially conflicting changes affecting the same application, CI, environment, or dependency. Conflicts should be reviewed before proceeding.

42. What do you check before a production go/no-go?

  • Required approvals are complete.
  • Risk assessment is complete.
  • Testing and UAT are complete.
  • Correct production artifact and version are confirmed.
  • Implementation and rollback plans are ready.
  • Dependencies are understood and ready.
  • Change window is confirmed.
  • No unresolved conflicts exist.
  • Required technical and support teams are available.
  • Validation and monitoring steps are ready.

43. What if the application team is not ready during the approved window?

The deployment should not be forced simply because the window was approved. Readiness should be reassessed, stakeholders informed, and the change rescheduled or updated according to the established process.

7. CMDB and Configuration Items

44. What is a CMDB?

A Configuration Management Database stores information about Configuration Items and their relationships. It provides a centralized view that supports impact analysis, change planning, incident resolution, and configuration governance.

45. What is a Configuration Item?

A Configuration Item is a component that needs to be managed because it participates in delivering or supporting a service. Examples include applications, servers, databases, services, network components, and other infrastructure or technology components.

46. What are CI relationships?

CI relationships describe how configuration items connect or depend on one another. For example, an application may depend on a database, API, server, middleware component, or external service. These relationships are important for impact analysis.

47. Why is CMDB important for release management?

An accurate CMDB helps identify what a change can affect. By reviewing affected CIs and their relationships, the release team can identify upstream and downstream dependencies, assess risk, coordinate teams, and reduce unexpected production impact.

48. What is the difference between a CI and an asset?

A CI is managed from a configuration and service perspective, while an asset is generally managed from a financial, ownership, inventory, or lifecycle perspective. A CI and an asset can be related, but they serve different purposes.

49. How would you review CMDB mapping for a new application?

I would identify the application CI and determine the related infrastructure, databases, APIs, services, middleware, integrations, and other dependencies. I would verify that the relationships accurately represent the application architecture and that the affected CIs can be used for impact and change analysis.

50. How do you maintain CMDB data quality?

Use defined ownership and governance, controlled CI creation, automated discovery or integrations where available, identification and reconciliation mechanisms, regular data-quality checks, relationship validation, and periodic cleanup of stale or duplicate records.

51. What are identification and reconciliation rules?

Identification rules help determine whether incoming data represents an existing CI or a new CI. Reconciliation controls which data sources are allowed to update CI information when multiple sources provide data.

52. What would you do if duplicate CIs appear?

I would identify why duplicates were created, review the identification process and source data, determine the authoritative record, correct the duplicate data according to the organization's CMDB governance process, and prevent the same condition from creating additional duplicates.

8. ServiceNow and CI/CD Integration

53. How does ServiceNow connect with a CI/CD platform?

ServiceNow provides change-management governance, approvals, risk information, and the audit record, while the CI/CD platform performs the actual build or deployment. Integration can associate the deployment with the approved change so the change, application version, pipeline execution, deployment time, and production result are traceable.

54. How can only approved changes be allowed into production?

The process combines ServiceNow approval controls with CI/CD controls. The production deployment requires the appropriate approved change, and where integration exists, the pipeline can validate the change information or approval status before allowing production deployment.

55. What information should be captured about a deployment?

The deployment should be traceable to the application version or artifact, pipeline or build, deployment time, implementation result, validation result, issues encountered, and final outcome.

9. Production Deployment and Validation

56. What is validated after production deployment?

Application health, deployment status, logs, monitoring, connectivity, health checks, key application functions, and other agreed validation or smoke tests are checked.

57. What if the pipeline says SUCCESS but the application is not working?

Pipeline success only confirms that the automated deployment steps completed successfully. I would check application logs, infrastructure or Kubernetes status where applicable, monitoring, health checks, connectivity, and recent configuration changes. If the issue cannot be safely stabilized and rollback criteria are met, the approved rollback process should be followed.

58. When is a production change considered successful?

When the deployment completes successfully, agreed validation or smoke tests pass, monitoring shows healthy behavior, and expected business functionality is confirmed.

10. Rollback and Failed Releases

59. What is a rollback plan?

A rollback plan explains how to return the application or environment to the previous stable state if the deployment fails. It should identify what needs to be reverted, how it will be performed, who is responsible, and how recovery will be validated.

60. When should rollback be initiated?

Rollback should be based on predefined criteria such as failed health checks, critical functionality failure, significant user impact, or an issue that cannot be stabilized within the agreed window. The decision should follow the approved recovery plan.

61. What happens if a production deployment fails?

First assess impact and stabilize the situation. Review pipeline, application, infrastructure, and monitoring information. If rollback is required, execute the approved rollback plan, validate recovery, continue monitoring, communicate status, and update the change record. If a production incident occurs, follow the incident-management process as well.

62. What if rollback also fails?

Escalate to the appropriate application, DevOps, infrastructure, database, integration, and support teams. The priority becomes restoring service. Follow additional recovery or remediation procedures, maintain stakeholder communication, and update the change and incident records.

11. Senior-Level Release Scenarios

63. A change is classified as High Risk, but the team wants to deploy tonight. What happens?

First confirm that the high-risk classification is accurate. If the risk is valid, the required high-risk approval and CAB process must be completed before deployment. A deadline should not be used to bypass change governance.

64. The application team completed testing but has no rollback plan. Should the release proceed?

For a significant production change, the recovery approach should be defined before proceeding. Testing confirms expected behavior, while rollback defines how to recover if production behavior differs from expectations. The rollback approach should be documented and reviewed before approval.

65. CAB approved the change, but the implementation plan changes just before deployment. What happens?

Determine whether the change remains within the approved scope. If the modification materially changes risk, impact, implementation, timing, dependencies, or rollback, the change should be reviewed and re-approved according to the organization's process.

66. A developer says, "It is only a small configuration change; no ServiceNow change is needed." What do you do?

First determine whether the change qualifies as a standard or otherwise pre-authorized change. If organizational policy requires a ServiceNow change, the production change should not bypass the process simply because the technical change is small.

67. A production deployment causes an incident. What happens?

The immediate priority is service restoration. Assess impact, perform rollback or remediation as appropriate, continue monitoring and communication, and update the ServiceNow change and incident records with deployment details, impact, recovery actions, and final outcome.

68. How is an end-to-end release made auditable?

Maintain traceability from application change through testing, ServiceNow change, risk assessment, approvals, deployment artifact, CI/CD execution, production validation, and final closure. This provides evidence of what changed, who approved it, when it was deployed, and what the result was.

14. Production and Troubleshooting

78. How do you troubleshoot a production deployment problem?

I first determine impact and scope. Then I review pipeline logs, deployment status, application logs, infrastructure status, monitoring, recent changes, configuration, connectivity, and dependencies. I identify whether the issue is application, infrastructure, configuration, deployment, database, integration, or environment related, then coordinate with the appropriate technical owners.

79. How do you handle a release blocker?

I identify the exact blocker, owner, technical dependency, business impact, and expected resolution. I track it, communicate the release risk, and determine whether it can be resolved within the window or whether the release needs to be rescheduled.

80. How do you communicate a technical problem to business stakeholders?

I focus on business impact, current status, risk, expected next step, owner, and decision needed. I avoid unnecessary technical detail unless it is relevant to the decision.

15. Modernization

81. How would you modernize an existing CI/CD process?

First understand the current process and identify manual steps, bottlenecks, failure points, inconsistent environments, and long release lead times. Then standardize pipeline templates, automate testing and quality checks, improve artifact promotion, strengthen environment controls, automate infrastructure where appropriate, improve monitoring, and establish measurable release metrics.

82. What CI/CD improvements would you recommend?

Standardized pipeline templates, automated testing, quality and security gates, versioned artifacts, consistent promotion between environments, controlled production approvals, better rollback capabilities, infrastructure as code, deployment metrics, and stronger monitoring and validation.

83. How would you evaluate an existing release process?

I would map the current lifecycle from code commit through production. I would identify manual handoffs, approval delays, repeated failures, dependency gaps, environment inconsistencies, deployment risks, rollback limitations, and missing visibility. Then I would prioritize improvements based on business impact and release risk.

16. AI and DevOps

84. How can AI tools help DevOps?

AI can help analyze pipeline failures and logs, generate or improve scripts, explain configuration, create test cases, draft documentation, summarize incidents, generate release notes, and assist with troubleshooting. Generated output should still be reviewed, tested, and validated before production use.

85. What is prompt engineering?

Prompt engineering means providing clear context, the objective, constraints, technical information, and expected output format so that an AI tool produces a more useful result. Prompts can then be refined based on the result.

86. Can AI replace DevOps engineers?

AI is better viewed as an accelerator. It can automate repetitive tasks and improve productivity, but architecture, risk assessment, production decisions, security, troubleshooting judgment, and business context still require human engineering responsibility.

17. Behavioral and Collaboration Questions

87. How do you handle disagreement between development and infrastructure teams?

I focus first on the technical dependency and evidence rather than ownership. I clarify what each team needs, identify the blocker, determine the release impact, assign actions and owners, and communicate the risk and timeline to stakeholders.

88. How do you handle pressure during a production release?

I focus on impact, facts, next action, and ownership. I keep communication clear, avoid unnecessary changes during an incident, follow the approved recovery process, and keep stakeholders informed while the technical teams work toward resolution.

89. How do you manage multiple teams during a release?

I establish the release scope, dependencies, owners, milestones, readiness criteria, communication path, and escalation path. I track blockers and risks and make sure each team understands its responsibilities and timing.

90. How would you work with a hands-on CI/CD engineer?

The CI/CD engineer can own the detailed pipeline implementation and automation. The release-management role provides technical oversight around what is changing, dependencies, environment readiness, risk, change management, release sequencing, approvals, and production readiness. The two roles should work closely rather than duplicate responsibilities.

19. High-Probability Scenario Questions

97. An application is ready, but the infrastructure environment is not ready. What do you do?

I would identify exactly what infrastructure dependency is missing, establish the owner and expected completion, determine the impact to the release, track it as a blocker, and communicate the risk. The application should not be considered production-ready until critical environment dependencies are resolved.

98. Two applications have a dependency on the same integration. One team wants to release before the other. What do you do?

I would understand the interface and compatibility requirements, determine whether the changes are backward-compatible, identify the required deployment sequence, review testing, and coordinate the release order. If the dependency creates unacceptable risk, the releases should be sequenced or separated.

99. A release has all approvals, but a new production issue appears before deployment. What do you do?

I would reassess the release based on the new information. I would determine whether the issue changes the risk or affects the same CIs or dependencies. If the new information materially changes the risk, the release should be paused and the change reviewed rather than relying blindly on the earlier approval.

100. A release is delayed because a dependency team is not ready. How do you handle it?

I would identify the dependency, owner, impact, and expected resolution. I would communicate the delay and options to stakeholders, determine whether the release can proceed safely without the dependency, and reschedule or re-sequence the release if necessary.

101. How would you handle five applications moving toward a common enterprise platform?

I would establish an application-by-application dependency and readiness view, identify shared integrations and infrastructure, define release sequencing, track environment readiness, coordinate testing, align ServiceNow changes, identify conflicts, and maintain visibility across current, in-flight, and upcoming releases.
