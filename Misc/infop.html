1. CI/CD & Jenkins

Q1. Explain your current CI/CD pipeline.

Answer: A typical flow starts when developers commit code to Git. Jenkins is triggered through a webhook or another configured trigger. The pipeline checks out the code, performs the build and testing, runs quality and security checks, publishes artifacts, and then proceeds with deployment. In my environment, Jenkins was also used to drive Kubernetes deployment workflows through DME and support Spinnaker deployments. After deployment, we validate the application and monitor it. If there is an issue, we investigate the logs and either correct the problem or roll back to the previous known-good version.

Q2. If you had to set up a CI/CD pipeline from scratch, how would you do it?

Answer: First I would understand the application build process, deployment target, environments and release requirements. Then I would configure source control integration, build and test stages, code-quality and security checks, artifact or container-image creation, artifact storage, deployment stages, approvals and monitoring. I would keep environment-specific configuration outside the application code and use secure credential management. Finally, I would add rollback and notification mechanisms.

Q3. What tools would you use to build the CI/CD pipeline?

Answer: The exact tools depend on the organization. A common stack could be Git or GitHub for source control, Jenkins or GitLab CI for pipelines, Maven or Gradle for builds, Artifactory for artifacts, Docker for containerization, Kubernetes for deployment, Helm for packaging, Terraform for infrastructure, SonarQube for quality checks, security scanners for vulnerabilities, and Grafana or another monitoring platform for observability.

Q4. What happens after a code commit?

Answer: A webhook or polling mechanism triggers the CI pipeline. Jenkins checks out the required branch and commit, runs the build and tests, performs quality and security checks, publishes the artifact or image, and then deploys it if all required gates pass. Depending on the environment, promotion to the next stage may require approval.

Q5. Explain the build → Docker image → deployment flow.

Answer: The pipeline first checks out the source code and builds the application. The resulting application artifact is included in a Docker image using a Dockerfile. The image is tagged with a meaningful version or commit identifier and pushed to an image repository. Kubernetes then pulls that image and deploys it using a Deployment, Helm chart, or another deployment mechanism. After deployment, readiness and application health are validated.

Q6. What Jenkins strategy did you use?

Answer: I worked with Jenkins-based CI/CD automation where Jenkins pipelines were used to build and deploy applications. My role included monitoring pipeline execution, analyzing failures, checking stage configuration and logs, and supporting deployment workflows. I also worked with Jenkins/Groovy-driven Kubernetes workflows that interacted with DME APIs and supported Spinnaker deployments.

Q7. What type of Jenkins pipeline did you use?

Answer: I have worked with Jenkins pipelines that use structured stages for activities such as checkout, build, validation and deployment. I have also supported Groovy-based Jenkins workflows. I would describe my experience primarily as supporting and troubleshooting Jenkins automation rather than claiming extensive Groovy application development.

Q8. What is the basic Jenkins CI/CD workflow?

Answer: Source code is committed, Jenkins is triggered, code is checked out, the application is built and tested, quality and security checks are performed, artifacts or images are published, and deployment is performed. After deployment, smoke tests and monitoring confirm the release.

Q9. How do you troubleshoot a failed Jenkins pipeline?

Answer: I first identify the failed stage and review the console output. Then I check recent code changes, pipeline configuration, environment variables, credentials, agent availability, workspace problems, dependencies and connectivity to external systems. I determine whether the failure is related to code, build, infrastructure, authentication or deployment. After fixing the root cause, I rerun the appropriate stage or pipeline and validate the result.

Q10. How do you integrate Jenkins with a Kubernetes cluster?

Answer: Jenkins can communicate with Kubernetes using credentials and the Kubernetes API. Depending on the setup, Jenkins can use Kubernetes agents or execute kubectl/Helm commands from an authorized build agent. Access should be limited using appropriate Kubernetes RBAC permissions. The pipeline then deploys manifests or Helm releases and validates the rollout.

Q11. How can you communicate with a Jenkins server running on Kubernetes?

Answer: I would first identify how Jenkins is exposed. It could be through an Ingress, LoadBalancer or internal Service. For troubleshooting, I would inspect the Jenkins Pod and Service: 
kubectl get pods -n jenkins
kubectl get svc -n jenkins
kubectl logs <jenkins-pod> -n jenkins
If necessary, port-forwarding can be used for temporary access.

Q12. How do you pull code from GitHub through Jenkins?

Answer: The Jenkins job is configured with the Git repository URL and credentials if the repository is private. Jenkins checks out the requested branch or commit using the Git plugin or pipeline checkout step. For secure environments, I prefer credentials stored in Jenkins rather than hard-coded in the Jenkinsfile.

Q13. Which Jenkins plugins would you install?

Answer: The plugins depend on the architecture. Common examples include Git, Pipeline, Credentials Binding, Docker-related plugins, Kubernetes integration, artifact repository integrations, SCM/webhook integrations and notification plugins. I would avoid installing unnecessary plugins because plugins increase the maintenance and security surface.

Q14. Where do you configure Docker credentials in Jenkins?

Answer: I would store them in Jenkins Credentials rather than directly in the Jenkinsfile. A pipeline can reference the credential by its ID and use it during the Docker login or image-push stage. Access should be restricted to the jobs that require it.

Q15. How do you authenticate GitHub with Jenkins?

Answer: For private repositories, Jenkins can use a personal access token, SSH key or an appropriate application-based integration. The credential is stored securely in Jenkins Credentials and referenced by the job. Webhooks can be configured so GitHub notifies Jenkins when changes are pushed.

Q16. How do you deploy an application to Kubernetes using a pipeline?

Answer: The pipeline first creates or obtains the application image. Then it authenticates to the target Kubernetes cluster and applies manifests or executes a Helm deployment. For example: 
kubectl apply -f deployment.yaml
kubectl rollout status deployment/myapp
With Helm: 
helm upgrade --install myapp ./chart -f values-prod.yaml
Finally, I validate Pods, Services, events and application health.

Q17. What stages have you used in your CI/CD pipeline?

Answer: Typical stages include checkout, build, unit testing, code quality, security scanning, packaging, artifact publishing, deployment and post-deployment validation. Depending on the application, additional stages can include database migration, approval and notification.

Q18. Which deployment strategies have you used?

Answer: Common strategies include rolling deployment, blue-green deployment and canary deployment. Kubernetes Deployments commonly use rolling updates. The appropriate strategy depends on application requirements, risk tolerance and whether traffic can be controlled between versions.

Q19. How do you perform a zero-downtime deployment?

Answer: I would use multiple application replicas, readiness probes, a Service or load balancer and a rolling-update strategy. Kubernetes gradually replaces old Pods while ensuring new Pods are ready. I would also configure appropriate maxUnavailable and maxSurge values and validate application health during the rollout.

Q20. How would you roll back a failed production deployment?

Answer: First I would confirm the failure and assess impact. If the previous version is known to be healthy, I would roll back to it using the deployment mechanism. With Kubernetes: 
kubectl rollout history deployment/myapp
kubectl rollout undo deployment/myapp
kubectl rollout status deployment/myapp
Then I would monitor the application and perform RCA separately.

Q21. Declarative vs Scripted Jenkins pipeline?

Answer: Declarative Pipeline provides a structured syntax with sections such as pipeline, agent, stages, steps and post. Scripted Pipeline provides more programming flexibility through Groovy. I prefer Declarative Pipeline when the workflow fits its structure because it is generally easier to read and maintain.

Q22. How do you manage Jenkins credentials/secrets?

Answer: I store credentials in Jenkins Credentials or an integrated secret-management system. Pipelines reference credentials by ID and should never print them. Permissions should be restricted, secrets should be rotated, and sensitive values should not be committed to source control.

Q23. How do you integrate Git/GitHub with Jenkins?

Answer: I configure the repository URL, branch and credentials in Jenkins and use webhooks to trigger builds. Jenkins checks out the required revision and executes the pipeline. Pull-request validation can also be configured depending on the repository workflow.

Q24. Webhook vs Poll SCM?

Answer: With a webhook, the source-control system notifies Jenkins when a change occurs. Poll SCM means Jenkins periodically checks the repository for changes. Webhooks are generally more efficient because they trigger the pipeline closer to the actual commit time without constant polling.

Q25. How do you implement approval before production?

Answer: I would place a manual approval gate between the staging and production stages. The approval should be associated with the release/change process and restricted to authorized users. The pipeline proceeds only after approval.

Q26. How do you deploy to multiple environments—Dev → QA → Stage → Prod?

Answer: I would promote the same tested artifact across environments rather than rebuilding different artifacts. Environment-specific configuration is injected through configuration files, Helm values, variables or secret management. Each environment has appropriate validation and, where required, approval gates.

Q27. How do you implement rollback?

Answer: Rollback should be designed before deployment. I keep the previous known-good application version available and use the deployment platform to restore it. For Kubernetes, rollout history and rollout undo can be used. For database changes, backward-compatible migration strategies should also be considered.

Q28. How do you add quality gates to Jenkins?

Answer: I would integrate tools such as SonarQube into the pipeline and define thresholds for quality or security findings. The pipeline should fail or stop promotion when the configured gate is not met. This prevents poor-quality code from moving to later environments.

Q29. How do you run stages in parallel?

Answer: Independent activities such as unit tests, static analysis and certain security checks can run in parallel. In a Declarative Pipeline, the parallel construct can be used: 
stage('Checks') {
    parallel {
        stage('Unit Test') {
            steps {
                sh './run-tests.sh'
            }
        }
        stage('Quality') {
            steps {
                sh './quality-check.sh'
            }
        }
    }
}

Q30. How do you troubleshoot a pipeline that worked yesterday but fails today?

Answer: I compare what changed since the last successful run. I check source changes, dependency versions, agent availability, credentials, certificates, external services, disk space, network connectivity and tool versions. I compare the failing logs with the previous successful build to isolate the change.

2. Kubernetes

Q31. Explain Kubernetes architecture.

Answer: Kubernetes has a control plane and worker nodes. The control plane includes the API server, scheduler, controller manager and etcd. Worker nodes run components such as kubelet, kube-proxy and the container runtime. The API server is the main interface, the scheduler places Pods on nodes, controllers maintain desired state and etcd stores cluster state.

Q32. You have a Pod in CrashLoopBackOff. How would you debug it?

Answer: I first inspect the Pod: 
kubectl get pod <pod>
kubectl describe pod <pod>
kubectl logs <pod>
kubectl logs <pod> --previous
I check container exit codes, events, probes, environment variables, mounted configuration, Secrets, resource limits and application logs. If the container is restarting, --previous is particularly useful.

Q33. The Pod is in CrashLoopBackOff, but the logs show no error. What would you check?

Answer: I would check Pod events, exit codes, liveness/readiness probes, container command and arguments, resource limits, mounted ConfigMaps and Secrets, and whether the application is terminating normally. I would also use kubectl describe pod and check previous-container logs.

Q34. How would you troubleshoot ImagePullBackOff?

Answer: I would run: 
kubectl describe pod <pod>
and inspect the Events section. I would verify the image name, tag, registry connectivity and imagePullSecrets. I would also check whether the image exists and whether the Kubernetes identity has permission to pull it.

Q35. What are the possible causes of ImagePullBackOff?

Answer: Common causes include an incorrect image name or tag, image not existing in the registry, authentication failure, missing imagePullSecret, registry connectivity problems, network restrictions or registry rate limits.

Q36. Given Kubernetes Pod information, identify the problematic Pod and explain your investigation.

Answer: I would look for non-running states such as CrashLoopBackOff, ImagePullBackOff, Pending or repeated restarts. Then I would inspect the specific Pod with kubectl describe pod, review events and logs, check resource availability, configuration, probes, image information and dependencies. I would compare it with a healthy Pod from the same workload.

Q37. What YAML files are required to deploy a three-tier application?

Answer: A typical three-tier application may have separate Deployments and Services for the frontend, backend and database. Additional YAML may include ConfigMaps, Secrets, PersistentVolumeClaims and Ingress. The exact set depends on the architecture.

Q38. What YAML files are required to host an application?

Answer: At minimum, an application commonly needs a Deployment and Service. Depending on requirements, it may also need ConfigMap, Secret, Ingress, PersistentVolumeClaim, ServiceAccount and autoscaling resources.

Q39. What is the difference between Ingress and Service?

Answer: A Service provides stable networking and load balancing to Pods. Ingress provides HTTP/HTTPS routing from outside the cluster to Services, usually based on hostnames or URL paths. An Ingress requires an Ingress Controller to actually implement the routing.

Q40. How would you implement URL/path-based routing in Kubernetes?

Answer: I would create an Ingress with path rules that route different URL paths to different Services. For example, /api can route to the backend Service while / routes to the frontend Service.

Q41. What happens when a Kubernetes Pod becomes unhealthy?

Answer: If the readiness probe fails, Kubernetes removes the Pod from Service endpoints so it stops receiving traffic. If the liveness probe fails repeatedly, Kubernetes restarts the container. Controllers such as Deployments ensure the desired number of replicas continues to exist.

Q42. How does Kubernetes recover an unhealthy Pod?

Answer: Kubernetes uses probes and controllers. A failed liveness probe can restart a container. If a Pod is terminated, a Deployment or ReplicaSet creates a replacement to maintain the desired replica count.

Q43. What are the Kubernetes worker-node components?

Answer: The main components are kubelet, kube-proxy and the container runtime. Kubelet manages Pods on the node, kube-proxy supports Service networking, and the container runtime runs the containers.

Q44. What is imagePullPolicy?

Answer: It controls when Kubernetes attempts to pull the container image. Common values are Always, IfNotPresent and Never. For tags such as latest, Kubernetes commonly defaults to Always. In production, immutable versioned image tags are preferable.

Q45. What challenges have you encountered during a Kubernetes upgrade?

Answer: Typical challenges include API-version compatibility, application compatibility, node upgrades, admission controllers, ingress components, Helm charts and third-party integrations. I would review release notes, validate workloads in a lower environment, back up important configuration and perform post-upgrade validation.

Q46. What checks do you perform after a Kubernetes upgrade?

Answer: I check node health, control-plane health where applicable, system Pods, application Pods, Services, Ingress, events, workloads, networking, storage and monitoring. I also validate critical application flows.

Q47. How do you verify that everything is working after a Kubernetes upgrade?

Answer: I check: 
kubectl get nodes
kubectl get pods -A
kubectl get events -A
kubectl get svc -A
Then I validate application endpoints, logs, metrics, ingress routing and critical business transactions.

Q48. Managed nodes vs self-managed nodes?

Answer: With managed node groups, the cloud provider handles much of the node lifecycle and integration. Self-managed nodes provide more control but require more operational responsibility for provisioning, upgrades, patching and lifecycle management.

Q49. Have you created a Kubernetes cluster? Explain the steps.

Answer: For a managed Kubernetes platform, the general process is to create the cluster control plane, configure networking and IAM/access, create node groups, configure add-ons and then deploy workloads. My experience has primarily involved working with Kubernetes/EKS environments, supporting deployments, troubleshooting and environment-level issues rather than claiming that I independently designed every cluster from scratch.

Q50. What are the different ways to create a Kubernetes cluster?

Answer: Clusters can be created using managed services such as EKS, AKS or GKE, using tools such as kubeadm for self-managed clusters, or through infrastructure automation platforms and Terraform modules.

Q51. How do you configure Kubernetes autoscaling?

Answer: Horizontal Pod Autoscaler scales Pod replicas based on metrics such as CPU or memory. Cluster Autoscaler adjusts node capacity when Pods cannot be scheduled because of insufficient resources. Vertical Pod Autoscaler can recommend or adjust resource requests depending on configuration.

Q52. How many Kubernetes clusters are you currently managing?

Answer: I would answer this based on the actual number in my current environment. A safe format is: "I support multiple Kubernetes environments across development and production. My responsibilities include deployment support, troubleshooting, configuration validation and coordination with platform teams."

Q53. Why isn't Cluster Autoscaler scaling up even though Pods are Pending?

Answer: I would check why the Pod is Pending and review Cluster Autoscaler logs. I would check node-group min/max limits, instance availability, resource requests, taints/tolerations, node selectors, affinity rules and cloud-provider permissions. The important point is that a Pending Pod must be unschedulable for a reason that Cluster Autoscaler can address.

Q54. HPA vs VPA?

Answer: HPA changes the number of Pod replicas. VPA adjusts or recommends CPU and memory resource requests for Pods. HPA is commonly used for horizontal scaling based on workload demand, while VPA addresses resource sizing.

Q55. During peak traffic, the Ingress Controller isn't routing requests efficiently. How would you diagnose it?

Answer: I would check Ingress configuration, controller logs, controller CPU/memory, replica count, Service endpoints, backend Pod health and application response time. I would also check load-balancer metrics, connection limits, DNS and network behavior.

Q56. How would you troubleshoot Kubernetes when Pods are healthy but users are receiving errors?

Answer: I would trace the request path from client to DNS, load balancer, Ingress, Service and Pod. I would check endpoints, ports, routing rules, TLS, application logs and dependency connectivity. Healthy Pods only prove that the containers are running; they do not guarantee the complete request path is working.

Q57. Deployment vs StatefulSet vs DaemonSet.

Answer: Deployment is commonly used for stateless applications. StatefulSet is used when workloads need stable identity or persistent storage characteristics. DaemonSet ensures a Pod runs on each applicable node, commonly for agents such as logging or monitoring components.

Q58. Service types: ClusterIP, NodePort, LoadBalancer.

Answer: ClusterIP provides internal cluster access. NodePort exposes a Service through a port on each node. LoadBalancer integrates with a cloud load-balancing service and provides external access when supported by the environment.

Q59. Readiness vs liveness probe.

Answer: Readiness determines whether a Pod should receive traffic. Liveness determines whether the container should be restarted because it is considered unhealthy. A readiness failure does not necessarily restart the container.

Q60. PV vs PVC.

Answer: A PersistentVolume represents storage available to the cluster. A PersistentVolumeClaim is a request for storage made by a workload. Kubernetes binds a suitable PV to the PVC based on requirements.

Q61. ConfigMap vs Secret.

Answer: ConfigMap stores non-sensitive configuration. Secret is intended for sensitive information such as credentials or tokens. Secrets still need appropriate access controls and secure handling; they should not be treated as automatically encrypted simply because the resource type is Secret.

Q62. How do you perform a zero-downtime Kubernetes deployment?

Answer: I use multiple replicas, readiness probes and rolling updates. The new Pods must become ready before old Pods are removed. I also validate the rollout and monitor application behavior: 
kubectl rollout status deployment/myapp
kubectl get pods

3. Docker

Q63. What is Docker and why is it used?

Answer: Docker packages an application and its dependencies into a container image. Containers provide consistent execution environments across development, testing and production. Docker is widely used in CI/CD because images can be built, scanned, stored and deployed consistently.

Q64. What is a Docker container?

Answer: A container is a running instance of an image. It provides process isolation while sharing the host operating system kernel. Containers are generally lightweight and can be started and stopped quickly.

Q65. How do you check whether a container is running?

Answer: I use: 
docker ps
docker ps -a
I can also inspect logs and container details: 
docker logs <container>
docker inspect <container>

Q66. How would you optimize a large Docker image?

Answer: I would use a smaller base image, multi-stage builds, a proper .dockerignore file, fewer layers where appropriate and avoid unnecessary packages. Build dependencies should not remain in the final runtime image.

Q67. You have frontend, backend and database components. Would you use one Dockerfile or separate Dockerfiles?

Answer: I would normally use separate images and Dockerfiles because the frontend, backend and database have different responsibilities and dependencies. The database would often be provided by a managed database service in production rather than packaged as part of the application image.

Q68. Where would you store Docker images?

Answer: I would use a container registry such as Amazon ECR, Azure Container Registry, Google Artifact Registry, Docker Hub or an enterprise registry such as Artifactory, depending on the organization.

Q69. A Docker container starts and then exits. How do you troubleshoot?

Answer: I would inspect logs and the container exit code: 
docker logs <container>
docker inspect <container>
docker ps -a
I would verify the CMD/ENTRYPOINT, required environment variables, configuration files and whether the application process is actually designed to remain running.

Q70. Docker image vs container.

Answer: An image is an immutable package containing the application and its dependencies. A container is a running or stopped instance created from that image.

Q71. Docker CMD vs ENTRYPOINT.

Answer: ENTRYPOINT defines the main executable, while CMD provides default arguments or a default command. They can be combined so the ENTRYPOINT remains fixed while CMD supplies default parameters.

Q72. How do you reduce Docker image size?

Answer: Use a suitable minimal base image, multi-stage builds, .dockerignore, remove unnecessary packages and files, and keep build tools out of the final image.

Q73. How do you handle Docker images as part of your CI/CD pipeline?

Answer: The pipeline builds the image, tags it with a unique version, scans it, authenticates to the registry and pushes it. The deployment references the immutable image tag. I avoid relying on mutable tags such as latest for controlled production releases.

Q74. How do you handle Docker image security/scanning?

Answer: I would scan images for known vulnerabilities before publishing or deploying them. I would also use trusted base images, minimize installed packages, avoid secrets in images and regularly update dependencies.

4. Terraform / Infrastructure as Code

Q75. Why do we use Terraform?

Answer: Terraform allows infrastructure to be defined as code, reviewed through source control and provisioned consistently. It supports reusable modules, dependency management and multiple cloud providers.

Q76. Why choose Terraform instead of AWS CloudFormation?

Answer: Terraform is cloud-agnostic and provides a common workflow across AWS, Azure, GCP and other platforms. CloudFormation is deeply integrated with AWS. If an organization is AWS-only, CloudFormation can be a strong choice; Terraform is attractive when portability and a common IaC workflow are important.

Q77. How do you use Terraform to deploy infrastructure?

Answer: I define infrastructure in Terraform configuration, initialize the working directory, validate and plan the changes, review the plan and then apply it: 
terraform init
terraform fmt
terraform validate
terraform plan
terraform apply

Q78. What infrastructure have you built using Terraform?

Answer: My experience includes working with Terraform-based automation and templates used as part of application onboarding and environment provisioning. I would describe my role accurately as supporting and validating Terraform-driven provisioning rather than claiming ownership of every infrastructure component.

Q79. Which AWS resources have you deployed with Terraform?

Answer: Examples include VPC-related networking resources, subnets, route tables, security groups, IAM components, compute resources and EKS-related infrastructure. The exact resources should be stated based on what I personally worked with.

Q80. What is Infrastructure as Code?

Answer: Infrastructure as Code means defining infrastructure using machine-readable configuration rather than manually creating resources. It makes infrastructure repeatable, reviewable and easier to automate.

Q81. What are the benefits of IaC?

Answer: Benefits include consistency, repeatability, version control, automation, peer review, easier recovery and reduced manual configuration errors.

Q82. What is the purpose of the Terraform state file?

Answer: Terraform state maps Terraform configuration to real infrastructure resources. Terraform uses it to determine what resources exist and what changes are required during planning.

Q83. What is a Terraform backend?

Answer: A backend determines where Terraform stores state and how state operations are handled. For example, an S3 backend can store state remotely and support locking through an appropriate locking mechanism.

Q84. Why do we use a Terraform backend?

Answer: Remote backends allow teams to share state safely instead of storing state only on an individual workstation. They can provide access control, versioning, encryption and state locking depending on the backend.

Q85. How do you secure a Terraform state file?

Answer: I use a remote backend with encryption, restricted IAM access, versioning and state locking where supported. I also avoid storing sensitive values unnecessarily and restrict access to the state because it can contain sensitive information.

Q86. How do you handle conflicts when multiple people modify infrastructure using Terraform?

Answer: Use remote state and locking, source control and a controlled workflow. Developers should create branches and review Terraform changes through pull requests. Only one apply should modify a state at a time when locking is enabled.

Q87. How do you handle Terraform state locking?

Answer: I use a backend that supports state locking. Before an apply, Terraform obtains the lock. Other operations that would modify the same state should wait or fail rather than simultaneously modifying the state.

Q88. What happens if the Terraform state stored in S3 is accidentally deleted?

Answer: The infrastructure still exists, but Terraform may lose its mapping between configuration and real resources. If state versioning is enabled, I would restore the appropriate previous state version. I would not immediately run apply because Terraform could interpret existing infrastructure as missing and attempt to recreate resources.

Q89. How would you recover the Terraform state?

Answer: If the backend supports versioning, restore the last known-good state version. If necessary, resources can be re-imported into Terraform state, but that requires careful mapping of configuration to existing infrastructure.

Q90. How would you prevent accidental Terraform-state deletion?

Answer: Enable state versioning, encryption, restricted IAM permissions and deletion protection where applicable. I would also use a dedicated state bucket and monitor administrative changes.

Q91. How do you import an existing VPC into Terraform?

Answer: First I define the corresponding resource in Terraform configuration. Then I import the existing resource into state: 
terraform import aws_vpc.main vpc-12345678
After import, I run plan and update the configuration so it accurately represents the existing resource.

Q92. What are Terraform providers?

Answer: Providers are plugins that allow Terraform to interact with APIs. Examples include AWS, Azure and Google Cloud providers. Providers expose resources and data sources that Terraform can manage.

Q93. What happens to providers after terraform init?

Answer: Terraform downloads or initializes the required provider plugins and prepares the working directory. Provider versions are typically tracked through the dependency lock file.

Q94. Can Terraform use multiple providers?

Answer: Yes. Terraform can use multiple providers in the same configuration. For example, infrastructure could use AWS resources along with another provider. Provider aliases can be used when multiple configurations of the same provider are required.

Q95. What are Terraform meta-arguments?

Answer: Common meta-arguments include count, for_each, depends_on, provider and lifecycle. They control how Terraform creates and manages resources.

Q96. count vs for_each?

Answer: count creates multiple instances based on a numeric count and uses numeric indexes. for_each creates instances based on a map or set and provides stable keys. for_each is often preferable when each resource needs a meaningful identity.

Q97. What is Terraform indexing?

Answer: Resources created with count use numeric indexes such as resource.example[0]. Resources created with for_each use keys such as resource.example["prod"].

Q98. What are Terraform modules?

Answer: A module is a reusable collection of Terraform resources and configuration. Modules help standardize infrastructure patterns and reduce duplication.

Q99. Why do you use Terraform modules?

Answer: Modules provide reusable patterns, consistency and easier maintenance. For example, an organization can have a standard VPC or EKS module and pass environment-specific variables to it.

Q100. What are Terraform workspaces?

Answer: Workspaces allow multiple Terraform state instances to be associated with the same configuration. They can be useful for certain environment patterns, although many teams prefer separate configurations or state backends for strong environment isolation.

Q101. What is Terraform drift?

Answer: Drift occurs when real infrastructure differs from what Terraform configuration and state expect, often because someone manually changed the resource outside Terraform.

Q102. A resource was manually changed in AWS but Terraform shows drift. What would you do?

Answer: I would review the plan to understand the difference and determine whether the manual change was intentional. If Terraform should own the setting, I would update the configuration if necessary and apply the desired state. I would avoid blindly applying changes until I understand the impact.

Q103. How do you safely deploy Terraform infrastructure changes to production?

Answer: I use source control, pull-request review, validation, Terraform plan, automated checks and approval before apply. The plan should be reviewed for destructive changes. Production applies should use controlled credentials and remote state locking.

Q104. What is immutable infrastructure in Terraform?

Answer: Immutable infrastructure means replacing resources rather than modifying them in place when changes require a new version. This makes environments more predictable and reduces configuration drift.

Q105. How does Terraform support immutability?

Answer: Terraform compares desired and actual state and can replace resources when a change requires replacement. Lifecycle settings such as create_before_destroy can sometimes help reduce downtime.

Q106. What happens if terraform apply fails halfway?

Answer: Terraform records successful changes in state as the operation progresses. Some resources may have been created while others failed. I would review the error, state and plan rather than manually guessing what exists. Then I would correct the root cause and run plan again.

Q107. How do you manage Terraform secrets?

Answer: I avoid hard-coding secrets in Terraform files. Secrets should come from a secure secret manager or CI/CD credential store. State must also be protected because sensitive values can sometimes appear there.

Q108. How would you structure Terraform for Dev/QA/Prod?

Answer: I would use reusable modules with separate environment configurations and separate state. Environment-specific variables would be maintained independently while the reusable infrastructure logic stays centralized.

Q109. How do you test Terraform before production?

Answer: I use formatting, validation, plan review, static analysis and policy checks. Changes should go through source-control review and a lower environment where practical before production.

Q110. How do you manage Terraform state in a team environment?

Answer: Use a remote backend, encryption, restricted permissions, state locking, versioning and source control. Production applies should run through an approved CI/CD process rather than individual unmanaged workstations.

5. AWS / Cloud

Q111. What AWS services have you worked with?

Answer: My experience includes AWS and Kubernetes environments, particularly EKS-related deployments and troubleshooting. Depending on the project, relevant services include EC2, VPC, IAM, load balancers, Route 53, CloudWatch, S3, RDS and EKS.

Q112. What is the CIDR range of your subnet?

Answer: The exact CIDR depends on the environment. CIDR defines the network address range and prefix length. For example, 10.0.1.0/24 provides a range of addresses within the 10.0.1.0 network.

Q113. How many route tables can a subnet be associated with?

Answer: A subnet can be associated with only one route table at a time. A route table can be associated with multiple subnets.

Q114. Would you modify an existing route table or create a new one? Why?

Answer: I would first understand whether the routing requirement applies to the existing group of subnets. If the desired route is common to those subnets, modifying the existing table may be appropriate. If the routing behavior needs to be isolated, I would create a separate route table.

Q115. What would you do if the existing route table doesn't allow the required modification?

Answer: I would determine the specific restriction and desired routing behavior. If necessary, I would create a new route table, associate it with the relevant subnet and validate the resulting network path.

Q116. Difference between public and private subnets?

Answer: A public subnet has a route to an Internet Gateway. Resources can have public connectivity if they also have the required public addressing and security configuration. Private subnets do not have a direct route to the Internet Gateway and commonly use a NAT Gateway for outbound Internet access.

Q117. Where are public/private subnets used?

Answer: Public subnets are commonly used for internet-facing load balancers or other resources that need public connectivity. Private subnets are commonly used for application servers, Kubernetes worker nodes and databases.

Q118. How does routing work?

Answer: A route table determines where network traffic should be sent based on destination CIDR. AWS evaluates the applicable route and forwards traffic to the configured target such as a local network, Internet Gateway, NAT Gateway, transit gateway or other target.

Q119. What is AWS Organizations?

Answer: AWS Organizations allows an organization to centrally manage multiple AWS accounts. It supports account grouping, centralized policies, governance and consolidated billing.

Q120. What is an SCP?

Answer: A Service Control Policy is an AWS Organizations policy that sets the maximum available permissions for accounts or organizational units. It does not itself grant permissions; IAM policies must still grant the required permissions.

Q121. Can an SCP contain Allow and Deny statements?

Answer: SCPs support Allow and Deny statements, but an SCP does not grant permissions by itself. Effective permissions require both an applicable SCP allowing the action and IAM permissions granting it.

Q122. How do you secure an AWS environment?

Answer: I would use least-privilege IAM, MFA, restricted network access, encryption, centralized logging, security monitoring, patching, secrets management, resource tagging and infrastructure-as-code controls. Production access should be tightly controlled and audited.

Q123. Which AWS security/compliance tools do you use?

Answer: Depending on the environment, tools can include IAM, CloudTrail, CloudWatch, GuardDuty, Security Hub, AWS Config and KMS. The exact tools should match the organization's security architecture.

Q124. Explain CloudWatch.

Answer: CloudWatch provides metrics, logs, alarms and monitoring for AWS resources and applications. It can be used to monitor CPU, network activity, application logs and custom metrics and to trigger alerts or automated actions.

Q125. Explain Route 53.

Answer: Route 53 is AWS's DNS service. It supports hosted zones, DNS records, health checks and routing policies such as weighted, latency-based and failover routing.

Q126. Explain Load Balancer.

Answer: A load balancer distributes client requests across healthy backend targets. In AWS, Application Load Balancers operate at the HTTP/HTTPS layer while Network Load Balancers operate at the transport layer and support high-performance TCP/UDP workloads.

Q127. How do you monitor AWS resources?

Answer: I use CloudWatch metrics and logs, alarms, application monitoring and centralized dashboards. Depending on the environment, Grafana can also visualize metrics from AWS and Kubernetes.

Q128. How do you configure Auto Scaling?

Answer: For EC2, I would configure an Auto Scaling Group with minimum, desired and maximum capacity and define scaling policies based on metrics such as CPU or request count. For Kubernetes, I would use HPA and, where required, Cluster Autoscaler.

Q129. What happens if an Auto Scaling Group doesn't launch instances during traffic spikes?

Answer: I would check scaling activity history, CloudWatch metrics and alarms, launch-template configuration, subnet capacity, security groups, IAM permissions, instance availability and service quotas. I would also check whether the desired capacity has actually changed.

Q130. An application behind an ALB returns HTTP 503. How do you troubleshoot?

Answer: I would check target health, target-group configuration, listener rules and application availability. Then I would verify that the backend Pods or instances are listening on the expected port and that security groups and networking allow traffic. ALB access logs and application logs can help identify the issue.

Q131. Users report slow application performance. Which AWS services/metrics do you check?

Answer: I would check ALB latency, target response time, EC2 CPU/memory where available, network metrics, database performance, application logs and Kubernetes resource utilization. I would correlate the timing with recent deployments or traffic changes.

Q132. An RDS database becomes unavailable. What is your recovery approach?

Answer: First I would determine whether it is an AWS service issue, database failure, network problem or application connectivity problem. I would check RDS status, events, CloudWatch metrics, connectivity and security groups. If recovery is required, I would use the configured Multi-AZ, failover, snapshot or backup strategy according to the organization's recovery plan.

Q133. How do you perform a zero-downtime deployment in AWS?

Answer: I would use multiple healthy instances or Pods behind a load balancer and gradually replace the old version. Health checks ensure traffic only goes to healthy targets. Blue-green or canary deployment can also be used when stronger release isolation is required.

Q134. EC2 is unreachable—what do you check?

Answer: I check instance status, system status checks, network interface, subnet routing, security groups, NACLs, route tables and connectivity. I also verify whether the instance has the expected public/private connectivity and whether the operating system itself is healthy.

Q135. Security Group vs NACL.

Answer: Security Groups are stateful and attached to resources such as EC2 network interfaces. Network ACLs operate at the subnet level and are stateless, meaning inbound and outbound rules need to be considered independently.

Q136. ALB vs NLB.

Answer: ALB operates at Layer 7 and supports HTTP/HTTPS routing such as host- and path-based routing. NLB operates at Layer 4 and is designed for high-performance TCP/UDP/TLS traffic.

Q137. IAM role vs IAM user.

Answer: An IAM user represents a long-term identity with credentials. An IAM role provides temporary credentials and is preferred for workloads and federated access where possible. Roles reduce the need for long-lived access keys.

Q138. What is a NAT Gateway?

Answer: A NAT Gateway allows resources in private subnets to initiate outbound connections to the Internet while preventing unsolicited inbound Internet connections to those private resources.

Q139. How does EKS work?

Answer: EKS is AWS's managed Kubernetes service. AWS manages the Kubernetes control plane, while workloads run on managed node groups, self-managed nodes or other supported compute options. EKS integrates with AWS networking, IAM and load-balancing services.

Q140. EKS Pod cannot connect to RDS—what do you investigate?

Answer: I would check DNS resolution, routing, security groups, NACLs, subnet configuration, RDS endpoint and port, Kubernetes network policies if applicable, and application credentials. I would also test connectivity from the Pod and review application logs.

Q141. How do you monitor AWS applications/infrastructure?

Answer: I use CloudWatch metrics and logs, AWS service-specific monitoring, alarms and dashboards. In Kubernetes environments I also use application logs, Pod metrics and Grafana dashboards. The key is to correlate infrastructure, application and deployment data.

6. Monitoring / Production Troubleshooting

Q142. What is Prometheus?

Answer: Prometheus is a monitoring and time-series database platform. It collects metrics, stores them as time-series data and provides PromQL for querying metrics. It is commonly used in Kubernetes environments.

Q143. What is Grafana?

Answer: Grafana is a visualization and dashboarding platform. It can connect to data sources such as Prometheus and display metrics through dashboards and alerts.

Q144. Why do we use Prometheus and Grafana?

Answer: Prometheus collects and stores metrics while Grafana provides visualization and dashboards. Together they provide visibility into infrastructure, Kubernetes and application behavior.

Q145. How do you monitor AWS resources?

Answer: I use CloudWatch metrics, logs and alarms, along with dashboards such as Grafana where available. I monitor resource utilization, availability, latency, errors and capacity.

Q146. How do you troubleshoot a failed Jenkins pipeline?

Answer: I identify the failed stage, inspect console logs and compare with the last successful run. I check code changes, credentials, environment variables, agents, workspace, dependencies and external systems. Then I fix the root cause and rerun validation.

Q147. Jenkins server is inaccessible—how do you troubleshoot?

Answer: I check whether the Jenkins process or Pod is running, then check CPU, memory, disk, networking and logs. If Jenkins is Kubernetes-based: 
kubectl get pods -n jenkins
kubectl describe pod <pod> -n jenkins
kubectl logs <pod> -n jenkins
I also check the Service, Ingress or load balancer.

Q148. Jenkins master is running out of disk space. What would you do?

Answer: I would identify what is consuming disk: 
df -h
du -sh *
Then I would review old workspaces, build artifacts, logs and caches. I would apply appropriate retention policies and increase storage if required. I would avoid deleting active build data without understanding the impact.

Q149. Build artifacts aren't getting uploaded to the artifact repository. How would you investigate?

Answer: I would check the pipeline logs around the upload step, repository URL, credentials, artifact path, network connectivity and repository availability. I would verify that the artifact was actually generated and that the pipeline has permission to publish it.

Q150. Application becomes slow after deployment. How would you troubleshoot it?

Answer: I would correlate the performance issue with the deployment. I would check application logs, CPU/memory, Pod restarts, response time, database performance, downstream dependencies and network behavior. I would compare metrics before and after the deployment and roll back if the release is clearly responsible and impact is significant.

Q151. Production deployment fails. How would you troubleshoot and recover?

Answer: First I would determine the deployment stage that failed and assess user impact. I would inspect deployment logs, Kubernetes events, application logs and configuration. If the failure cannot be corrected quickly and the previous version is healthy, I would roll back and then investigate the root cause.

Q152. Production deployment caused downtime. How would you perform rollback and RCA?

Answer: First restore service using the safest known-good version. Then collect deployment logs, monitoring data, application logs and change information. The RCA should identify the technical cause, contributing factors, why the issue was not detected earlier and preventive actions such as better testing, health checks or deployment gates.

Q153. Monitoring shows increased response time but infrastructure appears healthy. How would you investigate?

Answer: I would move up the stack from infrastructure to application behavior. I would check application logs, database latency, external APIs, thread pools, connection pools, garbage collection where relevant and recent application changes. Infrastructure being healthy does not necessarily mean the application is healthy.

Q154. Production disk utilization reaches 95%. What immediate and long-term actions would you take?

Answer: Immediately I would identify large files, logs, temporary data and old artifacts and safely reclaim space according to operational procedures. Long-term, I would implement log rotation, retention policies, monitoring thresholds and capacity planning.

Q155. Kubernetes Pods are healthy but users receive errors. How would you troubleshoot the complete request flow?

Answer: I would trace: 
Client
  ↓
DNS
  ↓
Load Balancer
  ↓
Ingress
  ↓
Service
  ↓
Pod
  ↓
Application
  ↓
Dependencies
At each layer I would verify connectivity, routing, health checks, ports, TLS, logs and metrics.

Q156. A Docker container keeps restarting in production. How would you identify the root cause?

Answer: I would check container logs, exit codes, health checks, resource limits and the application process. In Kubernetes I would use kubectl describe pod and kubectl logs --previous. I would also check whether configuration or secrets changed during deployment.

Q157. How do you perform root-cause analysis for a production issue?

Answer: I establish the timeline, identify what changed, collect logs and metrics, reproduce the behavior where possible and isolate the technical cause. Then I document impact, root cause, contributing factors, resolution and preventive actions.

Q158. Deployment succeeded but application does not work—what do you check?

Answer: I check Pod status, readiness probes, Service endpoints, Ingress rules, configuration, Secrets, application logs, image version and downstream dependencies. A successful deployment command only means Kubernetes accepted the desired state; it does not prove the application is functioning correctly.

Q159. How do you prioritize multiple production alerts?

Answer: I prioritize based on customer impact, severity, scope and business criticality. A complete production outage or widespread customer impact takes priority over a warning with no current user impact. I also look for related alerts that may have a common root cause.

Q160. What metrics do you monitor after a deployment?

Answer: I monitor error rate, response time, request volume, CPU and memory, Pod restarts, readiness, availability and key business/application metrics. I compare these with the pre-deployment baseline.

7. Git

Q161. How do you resolve Git merge conflicts?

Answer: I first update my local branch, perform the merge or rebase and identify conflicting files. I review the conflicting sections, choose the correct implementation, test the result and then commit the resolution. 
git status
git pull
git merge <branch>
# resolve conflicts
git add .
git commit

Q162. How do you choose a Git branching strategy?

Answer: I consider release frequency, team size, environment promotion and compliance requirements. A common model is feature branches with pull requests into a main or development branch, followed by controlled release promotion. The strategy should remain simple enough for the team to maintain.

Q163. How does Git integrate with Jenkins?

Answer: Jenkins connects to the Git repository, checks out the required branch or commit and runs the pipeline. Webhooks can notify Jenkins when changes occur. Jenkins can also report build or validation status back to the source-control platform.

Q164. Why did you choose Git as your source-control tool?

Answer: Git is distributed, widely adopted and supports branching, merging, history and collaboration. It integrates well with modern CI/CD platforms and code-review workflows.

Q165. If you push code to another branch, will Jenkins pipeline trigger?

Answer: It depends on the Jenkins trigger and branch configuration. If the webhook and job are configured to respond to that branch, the pipeline can trigger. If the job only monitors another branch, it will not.

Q166. Why do you push code to main branch?

Answer: In a controlled workflow, changes generally reach main through pull requests, reviews and automated checks. Direct pushes should usually be restricted for production repositories.

Q167. How do you authenticate GitHub with Jenkins?

Answer: Using an appropriate credential such as SSH credentials, a token or application integration. The credential is stored securely in Jenkins and referenced by the pipeline rather than hard-coded.

Q168. git merge vs git rebase.

Answer: Merge combines histories and creates a merge commit when necessary. Rebase moves commits onto a new base and creates a cleaner linear history. Rebase should be used carefully on shared branches because it rewrites commit history.

Q169. git revert vs git reset.

Answer: git revert creates a new commit that reverses an earlier commit and is safer for shared branches. git reset moves the branch pointer and can rewrite history depending on the option used, so it should be used carefully on shared branches.

Q170. What is HEAD?

Answer: HEAD is a reference to the currently checked-out commit or branch position. It represents the point from which the working tree is based.

Q171. How do you protect the main branch?

Answer: I would use branch protection rules requiring pull requests, code reviews and successful CI checks. Direct pushes and force pushes should be restricted according to the organization's policy.

Q172. What happens if someone accidentally pushes incorrect code to a shared branch?

Answer: I would first assess whether the change has already been consumed by downstream builds. For a safe shared-branch correction, I would normally create a revert commit, validate it through CI and communicate the impact. If the code has already reached production, the deployment rollback process may also be required.

9. Security / DevSecOps

Q185. How should secrets be managed in CI/CD?

Answer: Secrets should be stored in a dedicated secret-management system or CI/CD credential store and injected at runtime. They should not be committed to Git, embedded in Docker images or exposed in pipeline output.

Q186. How do you prevent credentials from appearing in Jenkins logs?

Answer: Use Jenkins Credentials rather than hard-coded values, use credential-binding mechanisms and avoid commands that echo secrets. Jenkins masking should be enabled, but I would not rely on masking alone.

Q187. How would you add security scanning to a CI/CD pipeline?

Answer: I would add appropriate scanning stages for source code, dependencies, container images and infrastructure. The pipeline can enforce severity thresholds so builds or deployments stop when critical vulnerabilities are detected.

Q188. How do you secure Terraform state?

Answer: Use encrypted remote state, restricted access, versioning and locking. State should be treated as sensitive because it can contain resource information and potentially sensitive values.

Q189. How have you used SonarQube?

Answer: I have worked with SonarQube as part of CI/CD quality validation. The pipeline can run analysis and evaluate the configured quality gate before allowing promotion to later stages.

Q190. What is SAST?

Answer: Static Application Security Testing analyzes source code or compiled code for security vulnerabilities without executing the application. It can be integrated into CI/CD to identify issues earlier in the development lifecycle.

Q191. What is container/image scanning?

Answer: Container scanning checks images for known vulnerabilities, outdated packages, insecure configurations and sometimes secrets. It helps prevent vulnerable images from being promoted into production.

Q192. How do you secure Kubernetes Secrets?

Answer: I restrict RBAC access, avoid committing Secrets to source control, use encryption at rest where supported and prefer an external secret-management solution when appropriate. Applications should receive only the secrets they need.

Q193. How do you control access to production deployments?

Answer: Use RBAC, least privilege, protected branches, CI/CD approvals and controlled deployment credentials. Production deployment should be auditable and ideally tied to an approved change or release process.

Q194. How do you secure cloud credentials used by pipelines?

Answer: Prefer short-lived credentials or workload identity over long-lived access keys. Restrict permissions using least privilege, store credentials securely, rotate them where necessary and audit their usage.
